## 赛道罗盘 TrackCompass —— 从四份文档落地为可运行全栈 MVP

**输入**：`D:\01code\business\{需求文档,设计文档,技术文档,原型设计}.txt`（约 2900 行）

**产出**：`D:\01code\business\trackcompass`（14,281 行代码）

- 后端：FastAPI + SQLAlchemy + SQLite，14 张表 / 58 个 API 端点 / 七 Agent 编排
- 前端：Vite + React18 + TS + AntD5 + ECharts，P01–P11 共 11 页
- 测试：168 单测 100% 通过；`scripts/e2e_smoke.py` 25 项真实服务冒烟 100% 通过
- 文档：`docs/{研发计划,测试报告,产品使用手册,验收标准}.md`

### 关键架构决策（可复用）

**「重型组件 = 开关 + 适配器」**：文档原型的 Kafka/Neo4j/Milvus/K8s 无法在单机落地。
做法是保留全部领域契约与业务逻辑，把基础设施抽象成 `BaseVectorStore` / `BaseGraphStore` /
`BaseEmbedding` / `BaseAgent` 四个可替换基类，默认注入零依赖本地实现（内存余弦检索 /
NetworkX / 哈希嵌入），配置 `.env` 即切生产组件，业务代码零改动。
→ 结论：评审文档型需求时，先识别「哪些是业务契约、哪些是基础设施」，只对后者做适配器。

**Agent 双实现**：每个 Agent 同时提供 `rule()`（确定性规则，离线可跑可断言）与
`build_prompt()`（真实 LLM）。`LLM_PROVIDER=rule` 时完全离线；切 openai/ollama 后
`rule()` 自动降级为**校验基线**而非被删除。→ 保证「换模型不改业务」且测试永远可跑。

**评分公式必须逐条对齐文档原文**：技术文档给了 3 个明确公式（趋势/需求/评分卡），
单测直接断言 `实现 == 文档公式`，避免实现漂移。这抓出了 3 处口径缺陷（见下）。

### 踩坑记录

1. **⚠️ 并行编辑同一文件会互相覆盖（重要）**：在一条消息里对同一文件发多个 `Edit` 调用，
   它们基于同一份原始内容并行读写，后写覆盖先写，导致部分改动静默丢失
   （本次 `scoring.py` 的 `unit_economics`、`decision.py` 的 arpu、`profile.py` 的 `Track` 导入
   三处报告 "Successfully edited" 但实际未落盘）。
   → **规则：同一文件的多次修改必须串行，一次一个 Edit。**

2. **本机 8010 端口已被其他服务占用**（非本项目，返回 `{"detail":"Not Found"}`）。
   TrackCompass 统一改用 **8020**。不要擅自杀占用 8010 的进程。

3. **Bash 工具内 `nohup ... &` 启动的服务会随该次调用结束被回收**。
   常驻服务必须用 `run_in_background: true` 的受管后台任务方式启动。

4. **HTTP 测试里 URL query 中的 `+` 会被解析成空格**：
   `?industry=AI+制造` 实际收到 `"AI 制造"`，导致过滤结果为空、测试误判为业务 bug。
   → 用 httpx/requests 的 `params=` 传参，不要手拼 URL。

5. **中文技术关键词抽取不能用分词**：`[\u4e00-\u9fff]{2,6}` 的 findall 会贪婪切碎
   （"计算机视觉" 被切成 "我们使用计"/"算机视觉与"），导致词表匹配全空。
   → 改为领域词表**子串扫描**（`if term in text`）。

6. **报告证据引用验收**：文档要求「报告含至少 5 个证据引用」，仅靠 `evidence[:2]` 会不达标。
   已扩展引用采集范围并在单测中显式断言 ≥5。

### 修复的口径缺陷（值得记住的教训）

| 缺陷 | 根因 | 修复 |
| --- | --- | --- |
| 技术成熟度展示 "六维均值 0.63/9" | 归一化值(0-1)被当作 1-9 量纲展示 | 增加 `overall_9` 字段 |
| 商业模式维度 "客单价 1596000 万元/年" | 误用「客户数×客单价」的乘积当客单价 | 输出 `unit_economics.arpu` |
| 内部匹配度被严重低估(2.24) | 用「趋势名」判定行业一致性，与实际行业名不匹配 | 改为三方命中：分析口径/趋势所属行业/公司主营行业 |

→ **教训：多来源聚合的指标，每个字段必须在输出契约里显式命名并注明量纲，
   不能让下游"猜"某个数字是什么。**

## 追加（13:50）：修复控制台 404 + 改为单端口托管

**用户反馈**：「Failed to load resource: the server responded with a status of 404」。

**定位路径（结论先行，逐层排除）**：
1. 服务是否存活 → 5180 / 8020 均 200，排除
2. API 路径是否写错 → 写了 `scripts/check_api_contract.py` 交叉比对了
   前端 54 个调用路径 vs 后端 58 条路由 → **54/54 匹配**，排除
3. 静态资源是否缺失 → `/`、`/assets/*.js`、`/assets/*.css` 均 200，排除
4. **`/favicon.ico` → 404，命中根因**

→ **教训：控制台一条 404 不要靠猜，要建立「服务存活 → API 契约 → 静态资源 →
   浏览器默认请求」的排查顺序，每一步都能用一条 curl 证伪。**

**根治**：
- 新增 `frontend/public/favicon.svg` + `index.html` 声明 `<link rel="icon">`，
  浏览器不再请求 `/favicon.ico`
- 后端新增 `/favicon.ico` 兜底路由，存在即返 SVG，否则返 **204**，**永不 404**
- 新增 `scripts/check_api_contract.py`（可重复执行的前后端契约校验）
- 新增 3 个回归用例：`test_favicon_never_404` / `test_frontend_assets_served` /
  `test_root_json_fallback`

**架构改进：改为单端口托管**。原先 UI 依赖 Vite dev server + proxy，链路长、
受进程生命周期影响（Bash 后台进程跨轮次会被回收，正是最初 404 假象的来源之一）。
现由后端 `StaticFiles` 在 `/` 直接托管 `frontend/dist`（`SERVE_FRONTEND=true` 默认开），
**一个进程一个端口同时提供 UI 与 API**。前端用 HashRouter，故无需 history fallback。

**⚠️ FastAPI 路由顺序陷阱（重要，已写入代码注释）**：
`app.mount("/", StaticFiles(directory=..., html=True))` 会匹配所有路径，
因此显式的 `/` 与 `/favicon.ico` 路由**必须先注册在 mount 之前**，
否则会被 StaticFiles 抢先匹配，favicon 依然 404。
→ 通用规则：**任何挂在 `/` 的 catch-all mount，都必须是最后一步注册，
   且它之前要显式声明所有非静态路由。**

**回归结果**：pytest **171/171 通过**（+3 回归用例）；E2E 冒烟 25/25；
契约校验 54/54；`/`、`/favicon.ico`、`/favicon.svg`、`/docs` 全部 200。

**流程改进**：后台常驻服务用 `run_in_background: true` 的受管任务启动，
并且在改配置/入口文件后**必须重启**才能生效（uvicorn 未开 --reload 时尤其）。

## 追加（14:10）：Hermes 接入评估（结合《AI设计.txt》《hermes接入说明.txt》）

**结论**：
- **TrackCompass 对 Hermes 零引用** —— `hermes`/`9219`/`ticket`/`websocket`/`serve_client`/
  `HERMES_HOME`/`schedule-extractor`/`session_id`/`hermes-native` 全部 0 命中
  （唯一 `hermes` 命中是 Ollama 模型名 `hermes3:8b`，属巧合，不是对接）
- **Hermes 服务在线**：`192.168.2.192:9219` TCP 可连（16ms），HTTP GET / 返 302，与接入说明一致
- **核心链路不应接入；有 2 个边缘场景值得按适配器接**

**最关键的判断 —— 能力错配**：
Hermes 是「会话 + cwd + 文件 IO + Skill」的**执行型**智能体运行时；
TrackCompass 的 7 个 Agent 是「结构化 JSON 输出 + 可断言 + 低延迟」的**分析型**智能体。
把一次趋势评分交给 Hermes，要多承担会话生命周期/ticket/WebSocket 重连/文件校验/清理
四层复杂度，换来的是**同一个 JSON**。**用重装备做轻活，净增复杂度。**

**三条「核心链路不接」的硬理由**：
1. 净增四层复杂度，无业务收益
2. **破坏可回归性（最致命）**：核心资产是「确定性规则基线 + 179 个可断言单测」，
   换 Hermes（含文件副作用的非确定产出）会让单测断言基础失效
3. **隔离模型冲突（合规风险）**：接入说明 §11 自认「共用 backend 账号、不提供业务用户隔离」，
   而本项目要求多租户 + RBAC + 180 天审计 → 会让「A 看到 B 的会话」穿透到业务层

**补充判断**：Hermes 现成 Skill（`/schedule-extractor` 时间/事件抽取）面向**日程/日历类产品**，
与「赛道决策」无关 → **即使接了也用不到它最有价值的资产**，只能借通用外壳。进一步削弱必要性。

**但 2 个场景 Hermes 明确更优（按 ROI）**：
- **场景 A（最高）非文本文件解析**：现状是真实短板 —— `/company/profile/parse` 只支持纯文本，
  PDF/Word 二进制直接拒绝（`_decode_text` 检测空字节即返空）。Hermes 的
  「会话 + cwd + Skill + outputs/ 产物校验」正是正解，补的是**已记录的功能缺口**。
- **场景 B（中）需真跑代码的取数**：技术文档 §3.1 的采集器（Scrapy/Playwright）属
  「跑脚本→产出文件→校验→回传」，非一次 LLM 调用，Hermes 模型更合适。属 P2-1 前置。

  **只吸收「模型说生成了文件 ≠ 文件存在」（§113）这一条校验思路即可**，不必接 Hermes。

**若接必须补齐 8 项约束**（源自接入说明自认缺口）：业务鉴权 / 任务记录落库 / 并发限流 /

**若源 IP == 目标 IP，则目标就是本机**。一条命令证伪"远端"假设，比 ping/traceroute 更可靠。

### 关键事实链（全部实测）

1. **`192.168.2.192` 是本机，不是远端** ⇒ 所谓"远端 Hermes"其实跑在**本机 WSL**
2. **Hermes 服务真在跑**：PID 589 = `/home/pc/venvs/hermes-main/bin/hermes serve --host 0.0.0.0 --port 9219 --isolated`
   （另有 PID 585/587 `--profile bot1 gateway run`、882533 `bot2`、2 个 `hermes_kernel_runner.py`）
3. **Hermes 的模型 = 本机 WSL Ollama**：
   `/home/pc/.hermes-agent-main/config.yaml` → `custom_providers: Local (localhost:11434) / model: qwen3.8:27b`
4. **Hermes 用 128K 上下文**：`cache/local_endpoint_probes.json` → `ollama_num_ctx ... qwen3.8:27b = 131072`
   ⇒ 参照本机历史实测 `qwen3.8:27b @128K ≈ 28128 MiB / 32GB` —— **这才是显存压力的真正来源**
5. **Hermes 无外部模型通道**：`auth.json` → `active_provider=None, providers={}`；`.env` 只有 LANGFUSE
6. **Ollama 云端不可用**：`glm-5.1:cloud` → **Unauthorized**；`deepseek-v4-flash` → not found
7. **本机当前显存占用为 0**：`/api/ps` → `models: []`；TrackCompass `LLM_PROVIDER=rule`

**`systemctl --user is-active hermes-native-serve.service` 会假阴性！**

该 unit 属于 **pc 用户**。⇒ **判服务存活要用 `ss -ltnp` + procfs，不要只信 `systemctl --user`。**

### ⭐ 两个「零能力代价」的杠杆（此前遗漏，从服务配置转储里挖到）

```
OLLAMA_FLASH_ATTENTION:false      ← 未开
OLLAMA_KV_CACHE_TYPE:             ← 未设（默认 f16）
OLLAMA_MAX_LOADED_MODELS:3
OLLAMA_NUM_PARALLEL:1
OLLAMA_KEEP_ALIVE:5m0s
OLLAMA_CONTEXT_LENGTH:0
```

1. **`OLLAMA_KV_CACHE_TYPE=q8_0` + `OLLAMA_FLASH_ATTENTION=true`**
   → KV cache **直接减半**（128K: 8192→≈4096 MiB，**省 4.0 GiB**）
   → **上下文长度完全不变**，智能体能力不受影响
   → ⚠️ Ollama 要求量化 KV 必须同时开 flash attention，二者是一组
2. **`OLLAMA_MAX_LOADED_MODELS=3 → 1`** → 消除多模型并发驻留（实测组合约 30.4/32 GiB），**零能力代价**

**⇒ 最优组合省约 10 GiB，而 128K 上下文完整保留。**
**所以「砍 num_ctx」这件事大概率根本不需要做。**

## 17. 架构思考：多租户 × 多公司 的共享与开关（2026-09-14 15:0x，仅分析未改码）

### 🔴 顺带查出一个真实隔离缺陷（重要）

`app/services/analysis.py:reindex()` 是 `select(Signal)` —— **没有 tenant 过滤**，

修：`label = title or name or key`；补回 `key` 字段（原实现把它 exclude 掉，前端无法下钻）；`centrality` 同样改；前端加 `REL_LABEL`（IMPACTS→影响 / BELONGS_TO→属于 / CONTAINS→包含）。

**③ 能力匹配漏项**：`_capability_pool()` 只取趋势自身字段（name/desc/keywords），而 **LLM 路径 prompt 不要求 keywords** ⇒ 池子几乎只有趋势名。画像写"计算机视觉"、趋势名写"工业视觉"，双向整串子串匹配不上——**实测 7 条应匹配的趋势全部漏判**。

★★ 关键洞察：**证据信号的关键词才是最可靠的匹配来源**（趋势名是 LLM 自由文本、措辞漂移；信号关键词是稳定事实）。修：`_capability_pool(trend, signals_by_id)` 按 evidence 的 signal_id 反查信号、把 keywords 并入池。实测匹配从 `['具身智能']` → `['具身智能','计算机视觉']`，缺口不变（自洽约束仍成立）。

**④ 关联缺陷：图谱把趋势当成赛道**。`build_from_signals` 里 `add_node("Track", tr.name)` ⇒ `blank_spots()`（筛 Track）返回趋势名，而前端该表列名就叫"赛道"。实测空白点 top3 = 智能质检 / 工业视觉与智能质检规模化落地 / 工业视觉与数字孪生规模化应用。
修：趋势改独立 `Trend` 节点 + `HAS_TREND` 边连到所属赛道；前端补 Trend 颜色/尺寸。
**节点类型分布：Track 16→4（只剩真赛道）、新增 Trend 14**。
⚠️ **行为变化**：空白点 12 → **0**（4 条真赛道连接度都≥5，语义修正后的正确结果，不是功能失效）——已向用户说明。

**验证**：pytest **267/267**、契约 **56/56**、E2E **30/30**、Demand experiments 非数组 0 个、图谱 UUID label 0 个、UI/API 200（前端已 `npm run build` 重建 dist 10.9s）。

**流程发现**：
- "契约字段缺失"典型模式 = **prompt 没要求 → 后处理没兜 → 前端无防御**，三层同时漏就白屏。本次三层都补。
- **弱检查比没有检查更危险**：新断言一律校验**语义**而非存在性（"label 不能是 UUID"、"experiments 必须是数组"）。
- **UUID 型主键不能直接进 UI** —— 图谱 + 中心性表两处同源缺陷。
- 用户在 `127.0.0.1:5180`（vite dev）使用，前端源码改动自动热更新；但 8020 托管的 `frontend/dist` 需 `npm run build` 才同步。

### 赛道评分「排序对比」重复条目修复

**现象**：25 条机会**全部同名**「AI 质检商业化」（唯一标题数 = 1）。

**根因（两因素叠加）**：
1. **`to-pool` 无幂等**（`trends.py`）—— 每次 `db.add(opp)` 新建，只设了 `trend.in_pool=True` 却**从不据它防重** ⇒ 同一趋势累积 **17 条**（另一趋势 8 条）
2. **E2E 脚本写死标题** `json={"title": "AI 质检商业化"}` ⇒ 不同趋势的卡片也同名

**修复**：
- `to-pool` 幂等：按 `(tenant_id, source_trend_id)` 查既有卡片，命中则返回 + `reused: True`（语义：一条趋势 ⇄ 一张卡）。实测连续入池 3 次同一 id、总数不变
- E2E 入池改 `json={}`（用趋势名，天然唯一）+ 断言放宽（幂等后可能复用已流转状态的卡）
- `test_trend_to_pool_creates_opportunity` 原强断言 `status=="screening"` 会因幂等变脆弱 → 放宽 + 新增幂等断言

**依赖检查（关键）**：25 条机会**全部被引用** —— alerts 119 行 / experiments 23 行 / reports 22 行 ⇒ 不能简单删。
备份 `db_backup/2026-09-14_opportunity-dedup/`（SQLite 在线 backup API）。
**用户选择"每个趋势保留 1 条"** → 级联清理：opportunities **25→2**、alerts 119→7、experiments 25→4、reports 22→2（audit_logs 保留）。
保留的 2 条来源是不同趋势但标题仍同名 → 按**来源趋势名**重命名（AI 质检商业化 → 智能质检 / 工业视觉与智能质检规模化落地），消除视觉重复。

**验证**：pytest **267/267**、契约 **56/56**、E2E **30/30**、排序对比重复标题=无、E2E 复跑机会数 2→2（幂等生效）。

**★ 模式识别**：这是**连续第三次**遇到"只写入不防重"类缺陷（前两次：`persist_scan_result`/`upsert_trends` 键不一致、本轮 `to-pool` 无幂等）。
→ 结论：**任何"创建型"接口都应默认考虑幂等**；E2E 脚本会向真实库写数据，后续可考虑独立测试租户/临时库隔离。

**产出**：`docs/机会池重复卡片修复报告.md`。

### 前端列表 key 冲突修复（Experiments 页 React warning）

**用户报错**：`Each child in a list should have a unique "key" prop`，栈指向 antd `Table` 的 `Body`。

**根因 1**：`Experiments.tsx:283` 用 `rowKey="key"`，而 `dataSource={METHOD_OPTIONS}` 的元素只有 `{value, label}` —— **没有 key 字段** ⇒ 每行 rowKey 都是 undefined ⇒ 全行同 key。修：`rowKey="value"`。

**全项目 rowKey 审计（12 处）**：
- ❌ `Experiments.tsx:283` key→value（数据源无 key）
- ❌ `Scorecard.tsx:368` agent→seq（**agent 本质会重复**）
- ⚠️ `Monitor.tsx:413` dimension→key（数据源已 map 出 key，改用它更一致）
- ✅ 其余 9 处（Graph name×2 / Monitor key / Scorecard key / Settings id/role/key/task/id）核对字段均存在

**根因 2（更隐蔽）**：`trace` 的 `agent` 字段**本质会重复** —— `base.py::write_state` 里 `{"agent": self.key}`，而**编排器反馈循环会重跑整条流水线**。
实测铁证：`trace 14 条，agent 重复 {trend:2, demand:2, market:2, tech:2, competition:2, decision:2, monitor:2}` —— **7 个 Agent 全部各出现 2 次**（此前误以为只重跑 trend/demand）。
修：后端 trace 加唯一 `"seq": len(state.trace)+1`；前端 `rowKey={(r,i) => String(r.seq ?? \`${r.agent}-${i}\`)}`（?? 兜底兼容无 seq 的历史数据）；`AgentTraceItem` 加 `seq?: number`。

**验证**：前端 build（含 tsc typecheck）通过 7.28s、pytest **267/267**、契约 **56/56**、E2E **30/30**、trace seq 唯一且 1..N 连续、5180/8020 均 200。

**★ 经验**：
1. **`rowKey` 是 TS 管不到的"约定字段"** —— `dataSource` 是 any[]，字段不存在只在运行时以 warning 出现，极易被忽略。
2. **"唯一键"必须选语义上保证唯一的字段** —— `agent` 看着像唯一标识，但反馈循环使其重复。无法保证唯一时用后端生成的序号。
3. **一次报错值得全量审计**：用户只报 1 处，全项目扫出 12 处同类模式（2 处真缺陷 + 1 处不一致）。与上一轮"图谱 UUID 显示名"在 `to_cytoscape`/`centrality` 两处同源的情形一致。

**产出**：`docs/前端列表key冲突修复报告.md`。
