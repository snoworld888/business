# 前端会话态保持修复报告

> **触发**：用户 2026-09-16 ——「需求探针需要保留当前结果，用户切换其他按钮菜单，回来不能空白啊」
> **结论**：已修复（3 个页面），新增可复现的 UI 冒烟脚本；**核查中另发现一个更根因的缺陷**（需求探针结果恒为 0 条）——
> 用户裁决 ①扩默认数据源 + ③放宽需求强度口径后**当日闭环**（原 `L-15`，现 ✅）。
> **改动面**：前端 8 个文件 + 后端 2 个文件（Agent 口径 + 单测）+ 2 个脚本 + 4 份文档；
> **零数据库改动、零 `.env` 改动、零新依赖**。

---

## 一、问题与根因

### 1.1 现象

在「需求探针」点「开始分析」得到结果后，切到左侧菜单任意其他页再切回来，
页面回到 **「尚未执行分析」的空态卡片**，之前的关键词、数据源、痛点聚类、需求强度全部消失，只能重跑。

### 1.2 根因

应用用 React Router 切页 —— **路由一变，页面组件即被卸载**，组件内的 `useState` 全部归零。

`Demand.tsx` 把「用户手动触发」的产物全放在本地 state 里：`keywords / sources / industry / result`。
需求探针是一次**耗时操作**（接真实大模型时更明显），结果却只活在组件内存里，
一卸载就没了。这不是需求探针独有 —— 凡是「手动点击 → 等 → 出结果」的页面都踩同一个坑。

### 1.3 同类排查结果

| 页面 | 手动触发的产物 | 组件卸载后 | 判定 |
| --- | --- | --- | --- |
| **需求探针** `Demand.tsx` | 探针结果 + 3 个筛选条件 | 全部归零 | 🔴 **必修**（用户报告） |
| **趋势雷达** `Trends.tsx` | 「能力画像 × 外部信号」面板 + 筛选 | 面板消失、筛选重置 | 🔴 修（与 1.2 同因，且该面板是用户明确关心的能力） |
| **赛道评分** `Scorecard.tsx` | 七 Agent 分析明细 + 本次分析依据 | 面板消失 | 🔴 修（**全站最贵操作**，接真实模型约 47s，丢了要重跑） |
| 信号库 `Signals.tsx` | 采集报告 | 弹窗关闭、不自动重开 | ⚪ 不改（弹窗是一次性反馈，自动重开反而打扰） |
| 验证实验 / 决策报告 / 监控复盘 / 能力画像 | 筛选、选中项、Step 进度 | 重置 | ⚪ 暂缓 —— 见 `L-16`。这些是**低价值中间态**，能从后端立刻恢复或重置成本极低 |
| 其余页面的列表数据 | — | 重新拉取，**不会空白** | ⚪ 无需处理 |

判断标准（本次统一采用）：**只有「用户手动触发 + 等待时间可观 + 结果无法即时重取」的状态才值得持久化**。

## 二、修复方案

### 2.1 分层

```
frontend/src/api/uiState.ts            纯存储层（无 React）：readSessionState / writeSessionState / clearSessionState
frontend/src/hooks/usePersistentState  React 层：useState 的 drop-in 替代，值同步写入 sessionStorage
```

键名统一前缀 `tc:ui:`，约定 `页面:语义`（如 `demand:result`）。

### 2.2 为什么是 sessionStorage 而不是 localStorage

分析结果**有时效性**：今天跑的探针结论，明天打开应用还挂在页面上，会被误认为是新结果。
会话级（关闭标签页即失效）正好匹配「结果的有效期」这个语义。

### 2.3 结果必须能自证「它是按什么条件跑出来的」

筛选条件现在也会保留，于是出现一个新风险：**用户改了条件但没重跑，看到的是旧结果**。
所以三处都补了同一件事 —— 给结果打**条件 + 时间**标签：

- 需求探针：顶部一行 `上次分析 09-16 10:59（关键词 大模型 · 数据源 3 个 · AI+制造）` + 「清除结果」
- 需求探针：若表单条件与快照不一致，额外弹一条提示「检索条件已改动，下方仍是上一次分析的结果」
- 趋势雷达：面板右上 `扫描于 09-16 10:59`
- 赛道评分：两张卡片右上角标运行时间；**结果按 `opportunityId` 存**，换机会卡片时不串台

### 2.4 登出必须一起清

`api/client.ts::storage.clear()`（登出 **与** 401 自动失效都走这里）新增 `clearSessionState()`。
否则换个账号登录，页面上还留着上一个账号的分析结果。

## 三、核查中发现的根因缺陷：需求探针结果恒为 0

修复过程中做了一次真实数据核查，发现问题比「状态丢失」更根本：

**信号库实测类型分布（SQLite 直查，48 条）**

| 类型 | 条数 |
| --- | --- |
| `news` 产业媒体 | 20 |
| `paper` 论文 | 18 |
| `policy` 政策 | 10 |
| `social` / `forum` / `review` / `bidding` / `recruit` | **0** |

而需求探针前端「数据源」写死设计文档 §5.6 的**需求侧五类**（社媒/论坛/应用评论/招标/招聘），
后端 `demand.py:41` 按 `Signal.signal_type.in_(payload.sources)` 过滤
⇒ **两侧类型永不相交，`matched_signals` 恒为 0**。实测：

| 请求 | 命中信号 | 痛点类数 | 综合强度 |
| --- | --- | --- | --- |
| 默认五类（社媒/论坛/评论/招标/招聘） | **0** | 0 | 0.00 |
| 不限类型 + 关键词「大模型」 | **4** | 4 | 3.41 |
| `industry=AI+制造` + 关键词「机器人」 | 2 | 3 | 3.38 |

**⇒ 这不只是「结果被清掉」，而是「结果本来就是空的」。** 2026-09-15 清掉 40 条种子信号、
换成采集器抓来的真实信号之后，探针就再也没可能出数。

### 3.1 用户裁决与落地（2026-09-16）

用户选择 **① 扩默认选中库内已有类型** + **③ 放宽「需求强度」的语义定义**（不做 ②接通数据源，其仍属 `L-04`）。

**① 默认数据源 = 需求侧五类 ∪ 库内已有类型**（`Demand.tsx`）

- 首屏 `/signals` 返回存量后**自动补全**默认选中，实测默认选中 8 类；
- 只要用户**手动改过**（`sourcesTouched` 直接读会话态判定），就**不再覆盖**其选择；
- 选项**按证据强度分组**：「需求侧信号（用户发声，主证据）」/「补充信号（同样承载需求信息）」，
  每项标存量（`社媒（0）` `产业媒体（20）`）。

**③ 放宽需求强度口径**（`backend/app/agents/demand.py`）

| 改动 | 说明 |
| --- | --- |
| `SOURCE_TYPES` 拆分 | `DEMAND_SOURCE_TYPES`（社媒/评论/论坛/招标/招聘 = **主证据**）+ `CONTEXT_SOURCE_TYPES`（产业媒体/论文/政策 = **补充证据**） |
| 新增 `demand_pool(state)` | 统一取数口径：**需求侧优先排序 → 补充类型 → 全量兜底**；`rule()` 与 `build_prompt()` **共用同一份** |
| 修掉提示词自相矛盾 | `build_prompt` 原先自己算 `by_type(需求侧五类)`，而真正送进模型的 context 来自 `retrieve()`（全量）⇒ prompt 自称「以下是 **0** 条信号」却塞满一屏证据。现在两者同源，并**如实标注证据类型与主/补差别** |
| `_fallback_label` | 负面兜底桶增加 `news`（产业媒体常转述行业抱怨）；policy/paper 多为正向/中性，泛化纳入只会造出假痛点 |

**语义边界（必须写清，否则会被当成等价证据）**：需求侧信号有**直接的付费意愿与负面情绪表达**；
补充信号只体现**意向**（政策=强制性要求/补贴导向、论文=未解技术痛点、产业媒体=行业诉求与扩产意图）。
因此取数排序上需求侧优先，prompt 里也把这个差别交给模型自行判断。

**实测（默认 8 类，真实大模型，cache 为空 → 一次真实推理 18.2s）**

| 请求 | 命中信号 | 痛点类数 | 综合强度 |
| --- | --- | --- | --- |
| 默认 8 类 + 关键词「大模型」+ AI+制造 | **4** | **4** | **3.41** |
| 只选补充三类（产业媒体/论文/政策） | **4** | **4** | **3.41** |
| 只选需求侧五类 | 0 | 0 | 0.00（库内确无此类信号，**自洽**；接通数据源见 `L-04`） |

`L-15` 已闭环 ✅，`docs/产品使用手册.md` P06 已同步口径说明。

## 六、设计取舍（为什么这样做）

1. **不引入 keep-alive / 多页同时挂载**：那会让所有页面同时发请求、同时订阅轮询，改动面与副作用都远超收益。
2. **不做「后端缓存」**：探针已有 `task_id`、七 Agent 分析本就 `persist=true` 落库 —— 后端数据才是真值。
   本次只解决「前端组件卸载导致的内存态丢失」，不碰数据源。
3. **只持久化「值得的」状态**：见 1.3 的判断标准。信号库的采集报告是弹窗，自动重开反而打扰用户，明确不改。
4. **不留「看着像新结果」的旧结果**：凡是保留的结果都必须带条件 + 时间标签，条件变了还要显式提示。
5. **登出即清**：会话态跟着登录态生命周期走，避免跨账号串数据。
6. **放宽口径必须写清语义边界**：把「政策/论文/产业媒体也计入需求强度」简单说成「多接了几个数据源」是
   偷换概念 —— 两侧证据强度不同（有无直接的付费意愿与负面表达）。因此代码里拆成主/补两类常量、
   取数时需求侧优先、prompt 中如实标注，文档也照实写。
