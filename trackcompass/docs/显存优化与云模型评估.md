## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 云模型有限制吗？ | **有，且限制不小**：并发数（Free=1）、额度计费、**数据出境到美国/欧洲/新加坡** |
| 云模型能省显存吗？ | **能，彻底省**（不加载本地权重）。但要把**数据出境**与**并发排队**两个代价算进去 |
| `num_ctx` 降到 32K 影响什么？ | **显存省约 6.0 GiB**（实测）；**短任务完全无感，长会话/多轮工具调用会明显受限** |
| 但**没必要**砍上下文 —— 有更好的办法 | **KV 量化 `q8_0` + 开 Flash Attention**：省 4.0 GiB，**128K 上下文完整保留** |
| 零能力代价的省显存办法 | **`OLLAMA_MAX_LOADED_MODELS=3 → 2`**（保留 1 个嵌入模型共存位），**不损任何能力** |
| 最优组合 | KV 量化 + Flash Attention + `MAX_LOADED_MODELS=2` ⇒ **省约 4~6 GiB，智能体与 RAG 均不受影响** |
| 128K + 嵌入模型能共存吗？ | **能**（实测 18.54 GB）—— 但**必须让对话模型先驻留**，否则 27b 的 42.7 GiB 过估会驱逐嵌入模型 |
| 当前 128K 配置健康吗？ | 预测值仍偏高（42.7 GiB vs 实测 17.87 GB，**高估 2.4×**），但 q8_0 后**实际占用已降到安全区** |

> **核心建议：两个零能力代价的开关已落地（KV 量化 + `MAX_LOADED_MODELS=2`），`num_ctx` 完全不必砍。**

### 1. 最终生效配置

```
OLLAMA_HOST=0.0.0.0
OLLAMA_MAX_LOADED_MODELS=2        ← 原 3（D2 最终值；中途曾设为 1，按用户指示改回 2）
OLLAMA_FLASH_ATTENTION=true       ← 原 false
OLLAMA_KV_CACHE_TYPE=q8_0         ← 原未设置（f16）
```

留档文件：`scripts/ollama-override.conf`（可纳入版本管理）

### 2. 为什么 D2 必须是 2 而不是 1

**Ollama 的 `MAX_LOADED_MODELS` 把 embedding 模型一并计数。**
RAG / 向量检索依赖 `bge-m3` 常驻；若设为 1，则「向量化 ⇄ 对话」交替时
会把对方逐出显存 —— 而对话模型权重 15.3 GiB，每次重载首 token 从毫秒级涨到数十秒。

设 2 恰好容纳「1 个对话 + 1 个嵌入」的稳定组合。**这是本次 D2 修正的核心理由，用户判断正确。**

### 4. 实测验证结果（同一模型同一上下文，前后对比）

| 指标 | 优化前 | **优化后** | 变化 |
| --- | --- | --- | --- |
| `n_ctx` | 131072 | 131072 | **不变** ✅ |
| `flash_attn` | (未启用) | **enabled** | ✅ |

### 5. 🔴 关键实测：「对话模型 + 嵌入模型」能否共存

**结论：可以共存，但存在「加载顺序不对称」—— 必须让对话模型先驻留。**

| # | 组合 | 加载顺序 | 调度判定（Ollama 原始日志） | 结果 |
| --- | --- | --- | --- | --- |
| A | `qwen2.5:7b @8K` + `bge-m3` | 嵌入先载 | `fits alongside` predicted=5.5 GiB / avail 29.6 GiB | ✅ 共存（5.58 GB） |
| B | `qwen3.8:27b @32K` + `bge-m3` | 对话先载 | `fits alongside` predicted=1.1 GiB / avail 13.9 GiB | ✅ 共存（18.20 GB） |
| C | `qwen3.8:27b @128K` + `bge-m3` | **对话先载** | `fits alongside` predicted=1.1 GiB / avail 13.6 GiB | ✅ **共存（18.54 GB）** |
| D | `qwen3.8:27b @128K` + `bge-m3` | **嵌入先载** | `predicted to exceed ..., evicting` predicted=**42.7 GiB** / avail 29.6 GiB | ❌ **bge-m3 被驱逐** |

**阈值判定规律（本次实测得到）**

- 加载 **`bge-m3`** 时：预测仅 **1.1 GiB**（`num_batch=2048`）→ 只要对话模型已驻留就**必然可共存**
- 加载 **`qwen3.8:27b @128K`** 时：预测 **42.7 GiB**，而 GPU 可用仅 **29.6 GiB** → **无条件驱逐其他模型**
- 该驱逐与 `OLLAMA_MAX_LOADED_MODELS` **无关**：它是 `sched.go:551` 的显存预测闸门，
  在「数量上限」判定之前就已触发

**根因：Ollama 对 27B@128K 的显存预测高估约 2.4 倍**

| | 预测值 | 实测占用 | 偏差 |
| --- | --- | --- | --- |
| `qwen3.8:27b @128K`（q8_0 KV） | **42.7 GiB** | **17.87 GB** | **高估 2.4×** |
| `bge-m3` | 1.1 GiB | 0.66 GB | 接近 |

预测值还含 `#prompt cache 8192 MiB`、`mmproj`（视觉编码器）、
`--spec-type draft-mtp`（投机解码）等项，因此偏保守。**这是 Ollama 侧行为，无法用配置消除。**

**实际运行影响（不是持续抖动，仅在冷启动时发生一次）**

```
对话模型已预热 → 本次 bge-m3 直接共存        （RAG 正常，无额外延迟）
对话模型已过期 → RAG 先加载 bge-m3           （此时 27b 若需加载，会驱逐 bge-m3）
```

即：**只要对话模型常驻，RAG 的嵌入调用不会再引发驱逐**。
建议（D7）：把 `OLLAMA_KEEP_ALIVE`（当前 `5m0s`）按业务节奏适当延长，可基本消除该冷启动边界。

## 三、问题 2：切云模型的使用限制

### 3.1 计划与限制（以官方定价页为准）

> ⚠️ 第三方资料对"额度如何计量"口径不一致（一说按 GPU 时间，一说按 token/credits），
> 且 Ollama **已多次调整云额度**。下表为多来源交叉整理，**最终请以 <https://ollama.com/pricing> 实时页面为准**。

| 计划 | 价格 | **并发云模型数** | 额度 | 模型范围 |
| --- | --- | --- | --- | --- |
| **Free** | $0 | **1** | 起步额度（按月/按窗口重置） | **仅 starter 模型**；加购 credits 才解锁全部 |
| **Pro** | $20/月（$200/年） | **3** | ≈50× Free（一说 $60 credits/月） | 更大的 pro 模型 |
| **Max** | $100/月 | **10** | ≈5× Pro（一说 $300 credits/月） | 最新模型 |
| Team | $500/月 | 10 | $1,000 credits/月（团队共享） | 全部 + 集中计费 |
| Enterprise | 定制 | — | 定制 | 访问控制、密钥级预算 |

**四条对你有实际影响的限制**：

1. **并发上限 = 排队，不是失败**。超出并发的请求**排队等待**，队列满则拒绝。
   → 这直接命中 TrackCompass：**七 Agent 的第 2 层是 3 个 Agent 并行**（市场测算 / 竞争情报 / 技术评估）。
   Free（并发=1）会把并行退化成串行，延迟约 ×3；Pro（并发=3）刚好够。
2. **按用量计费，重模型烧得快**。模型分 4 个用量档（level 1 `gpt-oss:20b` → level 4 `deepseek-v4-pro`）。
   官方明确建议 Free 档"只用 level 1–2 模型"。
3. **额度双时钟重置**：会话额度（约每 5 小时）与周额度（每 7 天）分别重置；90% 时邮件告警。
4. **无公开 SLA**（第三方评测指出 Ollama 云未发布 SLA，且吞吐/生产稳定性曾被诟病）。
   → 对"决策系统"这类要求可复现的场景，**不适合把云当唯一通道**。

### 3.2 🔴 最关键的一条：数据出境

Ollama 官方页面明确：**Cloud models in United States, Europe, and Singapore**。

也就是说，一旦切云模型：

| 会出境的数据 | 出处 |
| --- | --- |
| 政策 / 专利 / 融资 / 招聘 / 社媒 原始信号 | `signals` 表 |
| **公司能力画像**（技术栈、专利清单、人才结构、融资额、渠道、客户行业） | `company_profiles` 表 |
| 机会卡片、评分维度、竞品清单 | `opportunities` / `investment` 分析结果 |

而四份设计文档对此是**明确冲突**的：

- 《技术文档》§7.2：数据加密、**支持数据本地化**
- 《设计文档》§15 风险表：「**用户不愿输入内部数据 → 隐私保护、私有化部署**」
- 《需求文档》§八：「数据版权/隐私 → 合规采集，**企业数据本地化**」

> Ollama 声称「prompt 与响应数据不被记录、不被训练，并要求托管方零数据留存」——
> 这降低了**泄露**风险，但**不改变数据出境**这一事实本身。

**结论：云模型不适用于"含企业能力画像的分析链路"，只适合"公开信号级别的分析"或"非敏感的演示/验证"。**

### 3.3 云端可行性与成本估算（针对 TrackCompass 的真实用量）

实测单次完整分析的 token 量（来自 `_meta.prompt_chars`）：

| Agent | prompt | ≈tokens |
| --- | --- | --- |

| tech | 1,024 chars | ≈320 |
| **decision** | 17,023 chars | **≈5,320** |

**Free 档的额度大概率够用**；需要并行则升 Pro。

## 四、问题 3：`num_ctx` 降到 32768 的影响

### 4.1 显存收益（本机实测，非估算）

来源：`journalctl -u ollama` 中 `llama_context: n_ctx` 与 `llama_kv_cache: CUDA0 KV buffer size` 的配对记录。

**qwen3.8:27b（27.32B）**：

| 配置 | 权重 | KV cache | 合计 |
| --- | --- | --- | --- |
| **@128K（当前）** | 15,339.44 MiB | **8,192.00 MiB** | **≈23.0 GiB** |
| @64K | 15,339.44 MiB | 4,096 MiB | ≈19.0 GiB |
| **@32K** | 15,339.44 MiB | **2,048 MiB** | **≈17.0 GiB** |

**KV cache 与 `n_ctx` 严格线性**（对照实测：`qwen2.5:7b @32K → KV = 1,792 MiB`）。

> **128K → 32K 真实释放 ≈ 6.0 GiB**（不是此前粗估的 15GB —— 那个数字已修正）。

### 4.2 能力影响：实测 Hermes 到底用多少上下文

| 测量项 | 实测值 | 含义 |
| --- | --- | --- |
| `.skills_prompt_snapshot.json` | 37,374 chars ≈ **9,000 tokens** | 技能清单快照（**全量**注入时的上限） |
| `skills/` 目录 | 3.86 MB / 352 文件 | 技能正文**不可能全注入** ⇒ 实际是渐进披露 |
| `tool_discovery_cache.json` | 16,870 chars | 工具发现缓存（非注入 schema） |
| `tools/*.py` | **138 个** | 工具数量多，但按上下文筛选注入 |
| `memories/` | 509 bytes | 记忆占用可忽略 |
| **Ollama 日志中 Hermes 的实际 prompt eval** | **229 / 217 / 104 tokens** | **真实请求远小于 32K** |
| `context_length_cache.yaml` | `qwen3.8:27b → 131072` | 这是**它想要的**，不是**它用到的** |

### 4.3 🔴 决定性证据：128K 配置**已经越过安全线**，正在驱逐其他模型

Ollama 日志中明确记录了 **两次** 驱逐事件：

```
Sep 10 13:51:24  msg="llama-server model predicted to exceed available memory, evicting"
                 predicted="42.7 GiB"  predicted_num_ctx=131072  num_batch=512
                 available="29.6 GiB"  gpu_free="29.6 GiB"  system_free="26.1 GiB"

Sep 14 09:03:21  msg="llama-server model predicted to exceed available memory, evicting"
                 predicted="42.7 GiB"  predicted_num_ctx=131072
                 available="29.6 GiB"  gpu_free="29.6 GiB"  system_free="31.1 GiB"
```

**读法**：Hermes 以 128K 请求 qwen3.8:27b 时，Ollama 预测需要 **42.7 GiB**，
而实际可用只有 **29.6 GiB**（32 GB 卡上其余已被系统/桌面占用）
⇒ **被迫驱逐其他已加载模型**才能腾出空间。

2026-09-14 09:03 这次驱逐，正好发生在 **Hermes 今天启动时**（session `20260914_090416_6d8235`）。
本机历史记录也印证过：*「128K 上下文首次加载 Ollama 崩溃重启（PID 换号），复测成功 28128 MiB」*
—— 即预测值偏保守，重试后实际约 27.5 GiB 才加载成功，但**始终贴着上限在跑**。

> **结论：当前 128K 配置本身就处于"随时触发驱逐/重载"的临界状态。**
> 这不仅是显存占用问题，也是**运行稳定性与首 token 延迟**问题。

### 4.4 两个「零能力代价」的杠杆（此前遗漏，实测发现）

从 Ollama 服务的完整配置转储中读到：

```
OLLAMA_FLASH_ATTENTION:false      ← 未开启
OLLAMA_KV_CACHE_TYPE:             ← 未设置（默认 f16，16 位）
OLLAMA_MAX_LOADED_MODELS:3
OLLAMA_NUM_PARALLEL:1
OLLAMA_KEEP_ALIVE:5m0s
OLLAMA_CONTEXT_LENGTH:0           ← 未设默认，由每次请求决定
```

| 杠杆 | 操作 | 效果 | 能力影响 |
| --- | --- | --- | --- |
| **KV 量化** | `OLLAMA_KV_CACHE_TYPE=q8_0` + `OLLAMA_FLASH_ATTENTION=true` | **KV cache 直接减半**：128K 下 8,192 → ≈4,096 MiB，**省约 4.0 GiB** | **上下文长度完全不变**，仅有极小量化误差 |
| **单模型驻留** | `OLLAMA_MAX_LOADED_MODELS=1` | 消除其他模型并发驻留，实测最高省 ~6.3 GiB | **无** |

> ⚠️ Ollama 要求：使用量化 KV cache **必须同时开启 flash attention**（`OLLAMA_FLASH_ATTENTION=true`）。
> 二者是一组配置。

**这意味着：你完全不必牺牲上下文长度。** 先做这两个开关，
比"把 `num_ctx` 砍到 32K"更划算 —— 后者会实打实降低智能体的长会话能力。

### 4.5 各方案显存收益汇总（qwen3.8:27b）

| 方案 | 权重 | KV | 合计 | 相对现状 | 上下文能力 |
| --- | --- | --- | --- | --- | --- |
| 现状 128K / f16 KV | 15,339 MiB | 8,192 MiB | ≈23.0 GiB | — | 128K（但触发驱逐） |
| **+ KV 量化 q8_0** | 15,339 MiB | **4,096 MiB** | **≈19.0 GiB** | **省 4.0 GiB** | **128K 不变** ✅ |
| + `MAX_LOADED_MODELS=1` | — | — | — | 再省可达 6.3 GiB | 不变 ✅ |
| `num_ctx` → 64K | 15,339 MiB | 4,096 MiB | ≈19.0 GiB | 省 4.0 GiB | 64K ⚠️ |
| `num_ctx` → 32K | 15,339 MiB | 2,048 MiB | ≈17.0 GiB | 省 6.0 GiB | 32K ⚠️ |

> **推荐组合（最优）：`KV q8_0` + `FLASH_ATTENTION=true` + `MAX_LOADED_MODELS=1`**
> ⇒ 省约 **4.0 GiB（KV）+ 最多 6.3 GiB（并发驻留）≈ 10 GiB**，
> 且 **128K 上下文能力完整保留**，智能体不受任何影响。

### 4.6 分场景判断：如果仍要降 `num_ctx`

| 场景 | 实际 prompt 量级 | 32K 是否够 |
| --- | --- | --- |
| 日程抽取（`/schedule-extractor`，短文一句话） | 数百 token | ✅ 绰绰有余 |
| 单文件解析（PDF/Word 抽取） | 1–5K | ✅ 够 |
| 一问一答 / 短任务 | < 2K | ✅ 够 |
| **多轮工具调用**（读大文件 + 命令输出累积） | 累计 10–30K | ⚠️ **临界，会更早触发压缩/截断** |
| **超长会话**（连续数小时对话不清理） | 可能 >32K | ❌ **会截断，靠压缩维持** |
| TrackCompass 七 Agent 分析 | 单次最大 5.3K | ✅ 8K 都够 |

**一句话：短任务无感，长会话会变"记性差"。所以优先用 §4.4 的零代价杠杆，别急着砍上下文。**

### 4.4 ⚠️ 一个容易忽略的副作用：模型重载抖动

Ollama 是按 **`n_ctx` 分组调度**的（日志可见 `n_ctx_slot`）。
如果不同调用方传不同的 `num_ctx`，会创建**不同的 runner**，导致**模型反复加载/卸载**：

- 现象：每次切换调用方都要重新加载 15.3 GiB 权重 → 首 token 延迟从毫秒级涨到数十秒
- 含义：**不能只给 Hermes 单独降 `num_ctx`**，除非给 TrackCompass 换用**另一个模型**

## 五、推荐方案（按优先级）

### 🥇 第一步：KV 量化 + 开 Flash Attention —— **省 4.0 GiB，上下文不变**

```ini
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment="OLLAMA_FLASH_ATTENTION=true"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
```

- 收益：128K 下 KV cache **8,192 → ≈4,096 MiB，省约 4.0 GiB**
- 能力影响：**上下文长度完全不变**（128K 照旧），仅有极小量化误差
- 附加收益：Flash Attention 本身还能**加速长上下文推理**

### 🥈 第二步：`MAX_LOADED_MODELS` 3 → **2** —— **零能力代价，且保留 RAG 嵌入位**

```ini
Environment="OLLAMA_MAX_LOADED_MODELS=2"
```

**依据**：原值 3 允许 `qwen3.8:27b`(23.0 GiB) + `qwen2.5:7b`(4.1+1.8 GiB) + `bge-m3`(0.58 GiB)
≈ **30.4 GiB / 32 GiB** 三者并发驻留，这才是"显存挤占"的真实机制。

**但不能降到 1** —— Ollama 把 embedding 模型一并计数，降到 1 会让
RAG 的 `bge-m3` 与对话模型互相驱逐（对话模型每次重载 ~10s，代价远大于省下的 0.6 GiB）。
**取 2 = 1 个对话 + 1 个嵌入**，正好覆盖实际需要。

- 代价：切换**对话模型**时需重载（首次变慢）
- **不损失任何上下文能力，也不影响 RAG**

### 🥉 第三步：只在必要时才降 `num_ctx`

做完前两步后，若仍需余量再考虑（**这会实打实降低长会话能力**）：

| 选择 | 额外释放 | 适用 |
| --- | --- | --- |
| **64K** | ≈2.0 GiB（在 q8_0 基础上） | Hermes 有长会话/多轮工具调用需求（**稳妥折中**） |
| **32K** | ≈3.0 GiB | Hermes 只跑短任务（日程/提醒/单文件） |

### 第四步：若要真实模型但不想吃本地显存 —— 双模型分流

避免重载抖动（Ollama 按 `n_ctx` 分组调度，不同 `num_ctx` 会创建不同 runner）：

| 消费者 | 模型 | 上下文 | 显存 |
| --- | --- | --- | --- |
| Hermes | `qwen3.8:27b` | 128K（保留） | ≈19.0 GiB（q8_0 后） |
| TrackCompass（如启用真实模型） | `qwen2.5:7b` | 8K | 4.17 + 0.5 ≈ **4.6 GiB** |

配合 `OLLAMA_MAX_LOADED_MODELS=2`（本次已生效），
两者**可与 `bge-m3` 同驻**（实测 `qwen3.8:27b@128K + bge-m3` = 18.54 GB），不再需要交替重载。
TrackCompass 单次最大 prompt 仅 5.3K tokens，**8K 上下文绰绰有余**。

### 备选：云模型（受限使用）

仅在以下条件**同时满足**时采用：
1. 只分析**公开信号**，不含企业能力画像等内部数据
2. 接受国内 → **美国/欧洲/新加坡**的数据出境
3. 接受并发排队（Free=1 会让三层并行退化为串行）
4. 定位为**演示/验证通道**，不作为唯一通道（无 SLA）
