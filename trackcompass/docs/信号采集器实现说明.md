# 信号采集器实现说明

> 对应《技术文档》§3.1「数据源接入」与 §3.2「数据管道」
> 实现日期：2026-09-15　｜　状态：已上线运行，实测通过

---

## 1. 解决的问题

在此之前，系统的信号层是**空的**：40 条信号全部硬编码在 `backend/app/seed/__init__.py`
的 `RAW_SIGNALS` 里，`url` 一律是 `https://example.com/...` 占位，全仓库
**0 行抓取代码**。

后果是连锁的：

```
没有真实信号 → 趋势只能从假数据聚类 → 能力匹配的「情报空白」无法消解
            → 雷达的可信度只等于演示数据的可信度
```

本次按设计把这条链路补齐，**信号层现在是真实采集的**。

### 2.2 数据管道（《技术文档》§3.2）

设计写的是：

```
数据源 → 采集器 → Kafka → 清洗/标准化 → 实体抽取 → PostgreSQL/Neo4j/Milvus
```

本地部署版把 Kafka 换成**同步编排**（量级不到需要消息队列的程度），其余环节一一对应：

| 设计环节 | 本实现位置 |
| --- | --- |
| 采集器 | `app/collector/sources/*.py` |
| 清洗/标准化 | `app/collector/normalize.py` |
| 实体抽取 | `app/agents/base.py::extract_tech_keywords`（复用既有能力） |
| 写入关系库 | `app/services/signal_ingest.py` |
| 图谱 / 向量 | `app/services/analysis.py::reset_and_reindex` + `refresh_graph` |

### 2.3 采集频率（《技术文档》§3.1）

设计给的频率已落到适配器的 `frequency` 属性上，调度侧可用 `--frequency` 分组调用：

## 6. 如何启用需要密钥的源

`keyed_sources.py` 里的适配器**请求逻辑已按官方文档写好**，填入密钥即生效：

```bash
# backend/.env
PATENTSVIEW_API_KEY=xxx     # https://search.patentsview.org/docs/
CRUNCHBASE_API_KEY=xxx      # https://data.crunchbase.com/docs
RECRUIT_API_KEY=xxx         # 招聘：需按目标平台自行实现 _fetch_keyed
SOCIAL_API_KEY=xxx          # 社媒：需开放平台资质
SUPPLY_API_KEY=xxx          # 供应链：需行业数据库授权
```

填好后 `--list` 中该源变为 `✓`，默认启用集需要把它加进
`app/collector/registry.py::DEFAULT_ENABLED`（或调度时显式 `--sources`）。

> ⚠️ **诚实标注**：这五个适配器的参数结构依据官方文档编写，但**未在本机联网验证**
> （没有密钥）。首次启用请先 `--dry-run`，必要时微调 `_to_signal()` ——
> 解析逻辑与网络请求已分离，改动面很小。

## 7. 扩展新数据源

继承 `SourceAdapter` 并实现 `fetch()`，然后注册：

```python
# app/collector/sources/my_source.py
class MySourceAdapter(SourceAdapter):
    key = "my_source"
    signal_type = "news"          # 必须落在 SignalIn 的 Literal 取值里
    name = "我的数据源"
    frequency = "daily"

    def fetch(self, ctx: CollectContext) -> list[RawSignal]:
        data = self.client.get("https://api.example.com/items",
                               params={"q": ctx.first_keyword()}, expect="json")
        return [RawSignal(signal_type=self.signal_type, source=self.name,
                          title=item["title"], content=item["body"],
                          url=item["link"], published_at=parse_datetime(item["date"]))
                for item in data["items"]]

# app/collector/registry.py → ADAPTERS 里加一行，再决定是否进 DEFAULT_ENABLED
```

清洗、去重、实体抽取、入库、建索引**都由既有管道自动处理**，无需重复实现。

## 8. 关键设计决策与踩坑

| 决策 / 坑 | 说明 |
| --- | --- |
| **零新增依赖** | 只用 `httpx` + 标准库（`xml.etree` 解析 RSS、`html.parser` 解析 HTML），保持 `requirements.txt` 的「offline-friendly core」约定 |
| **arXiv 不可用** | 实测 `export.arxiv.org` 返回 `Rate exceeded`（共享出口 IP 被限），改用 OpenAlex + Crossref |
| **gov.cn 的 JS 跳转** | `zhengce/zuixin.htm` 是跳转页，真正入口是政策文件库的 JSON 检索接口 |
| **ccgp 搜索接口反爬** | `search.ccgp.gov.cn` 返回「频繁访问」页，改用列表页 + HTML 解析（URL 内嵌日期，无需解析相对时间） |
| **招标源必须给检索词** | 列表页无检索能力，无词时会拉回全量无关公告 → `requires_keywords=True`，运行器跳过并如实上报 |
| **相对链接必须基于列表页** | ccgp 的 `href="./gkzb/...` 若基于站点根拼接会丢 `/cggg/zygg/` → 404 |
| **论文源不能按日期排序** | `sort=publication_date:desc` 会把相关性排序覆盖掉，实测搜「计算机视觉」返回《泛逻辑分析》→ 去掉 sort 用默认相关性 |
| **源主题标签不进 keywords** | OpenAlex topics / Crossref subjects 是英文标签，与中文能力词体系匹配不上，混进去只污染趋势聚类 → 移到 `metrics` |
| **行业归属优先级** | 信号自带 > 内容推断（标题权重 ×3）> 公司行业兜底。**不能**让公司行业优先，否则所有外部信号被打成同一行业，赛道差异消失 |
| **入库去重必须一处** | 此前 `POST /signals` 只算 `content_hash` 却不判重 → 反复调用会灌重复数据。现统一走 `signal_ingest.persist_signals`，按 hash + url 双重判重 |
| **逐源入库而非汇总** | 每源独立事务，`inserted`/`duplicated` 归因精确，单源失败不连带回滚 |
| **循环导入** | `signal_ingest → collector.normalize` 会触发包 `__init__` → 加载 runner → 回头导入 signal_ingest。改用 PEP 562 惰性导出 |

## 11. 种子信号清理记录（2026-09-15）

采集跑通后，40 条演示信号已从库中移除，让雷达完全基于真实数据。

**依赖核查揭示的问题**：直接删信号是不够的 ——

| 依赖 | 实测 | 处理 |
| --- | --- | --- |
| 趋势证据引用 | **47 条趋势中 44 条**的证据含种子信号，其中 **43 条证据全部是种子** | 删除这 44 条（它们本就是假数据产物）；保留 3 条纯真实数据生成的趋势 |
| 机会卡片 | 2 条通过 `source_trend_id` 指向被删趋势 | 置空该字段（避免悬空引用） |
| **RAGFlow 侧残留** | `index()` 是**幂等追加**、不会删除已失效文档 ⇒ **79 篇**已删信号仍留在 dataset 里会被召回 | 用 `RAGFlowEngine.drop()` 按 signal_id 清除 |

清理结果：

```
signals        88 → 48   （全部为真实采集）
trends         47 →  3   （保留的 3 条证据不含种子信号）
opportunities   2 →  2   （source_trend_id 置空）
RAGFlow 文档   127 → 48   （清除 79 篇失效）
图谱           334 节点 / 441 边 → 232 节点 / 284 边
```

**防复发**：`seed_all(db, with_signals=False)` + `bootstrap(with_signals=False)`，
`scripts/start-all.sh` 的 `bootstrap(seed=True)` 因此不再写入演示信号。
测试（`tests/conftest.py`）显式保持默认 `True`，确保 pytest 仍可离线断言。

备份：`backend/db_backup/2026-09-15_remove-seed/trackcompass.db`

> 📌 **通用教训**：删除数据时必须同时检查**派生数据**（趋势/机会）与**外部索引**
> （RAGFlow / 向量库 / 图谱）。本项目里 RAGFlow 的 `index()` 是幂等追加语义，
> 不做反向清理 ⇒ 只删库内数据会导致「**已删除的信号仍被检索召回**」，
> 且这种残留不会报错，极难察觉。

## 12. 清理连带修复的两个缺陷（2026-09-15）

删除种子信号后跑回归，暴露出两个此前被假数据掩盖的问题。

### 12.1 抽词规则把英文噪声收进了关键词（影响趋势标签）

**现象**：趋势标签里出现 `'Military Technology and Strategies'`、
`'Neural Networks and Reservoir Computing'`、`'https'`、`'of'`、`'Zhang'`。

**根因**：论文类信号的正文是**英文摘要 + OpenAlex 英文主题**，而
`extract_tech_keywords` 的英文匹配只要求「长度 > 1 且是 ASCII」：

```python
ascii_terms = re.findall(r"[A-Za-z][A-Za-z0-9+#.\-]{1,20}", text)
if not (len(mapped) > 1 and mapped.isascii()):   # ← 过宽
    continue
```

⇒ 摘要里的普通词（`Rough`/`Sets`/`Military`）、URL 片段（`https`/`kr.com`）、
作者名（`Zhang`）、文献格式词（`of`/`in`/`vol`）全部被当成"技术词"，
再经 `trend_tags` 传染到趋势的 `_tags`。

> 注：此前已修过「源主题不进 `keywords`」，但那批信号是在修复**之前**采集的，
> 且 content 里的 `主题：...` 文本仍会被抽回 —— 属于修复不彻底。

**修复**：改为**形态白名单**（`_looks_like_tech_ascii`），只收四类：

| 类别 | 例 |
| --- | --- |
| 显式白名单 `EN_TECH_VOCAB` | LLM / RAG / YOLO / Transformer / OpenCV |
| 含数字的型号 | `6G` / `BERT-base` / `GS-MGF-LPLs` |
| 全大写缩写（2–10 位） | `GPU` / `IoT` / `SaaS` |
| 驼峰式命名（≥2 个大写） | `OpenCV` / `TensorFlow` / `PyTorch` |

外加停用词表排除 URL 片段、文献格式词、作者名与**职位/融资轮次**
（`CEO`/`CTO`/`Pre-A`/`IPO`）。

实测效果：

```
英文论文摘要  → ['OpenCV', 'TensorFlow']           （此前 20+ 个噪声词）
36氪正文 URL  → []                                  （此前 ['https','kr.com','p']）
中文技术稿    → ['边缘计算','强化学习','计算机视觉','YOLO']
型号与缩写    → ['6G','GS-MGF-LPLs','BERT-base','GPU']
```

**数据侧同步**：对现有 48 条信号重新抽词（28 条有变化），
并回算全部趋势的 `_tags`（9 条有变化）。

### 12.2 E2E 脚本的断言写法会把「检查失败」变成「脚本崩溃」

**现象**：`e2e_smoke.py` 在需求探针一项直接抛 `IndexError`，整个冒烟中断。

**根因**：`check(名, 条件, 描述)` 的**三个参数都会先求值**，而描述串写了
`probe['pain_points'][0]['name']` —— 当 `pain_points` 为空时，描述求值先崩，
根本走不到断言。

**修复**：
1. 描述串改为**先算好**（判空后再取首项）；
2. 断言从「必须有痛点」改为「**请求-响应自洽**」——
   痛点来自社媒/评论/招标/招聘类信号，信号库里没有这些类型时输出为空是
   **正确行为**而非缺陷（实测 `matched_signals: 0` → `pain_points: []`，
   两者一致即为通过）。

> 📌 **通用教训**：**断言描述里不要放可能越界的取值**。这类缺陷在数据充足时
> 永远不触发（此前 88 条信号含社媒类型，痛点非空），一旦上游数据变化就炸 ——
> 属于「被数据掩盖的脚本缺陷」。

### 12.3 E2E 的「数据源覆盖」口径过时

同一轮回归还暴露：E2E 用 `GET /signals/sources` 的 `connected`（= **库里有数据的类型数**）
判定「覆盖 ≥5」，而设计 §7.2 的验收标准指的是**采集能力**（能接哪些源）。

种子数据时代这条恒为真（种子里含 9 类信号），删掉种子后只剩 policy/news/paper 三类 ⇒
误报失败。已改为读 `GET /signals/adapters` 的 `available`（当前 8/13），
并在描述里附带数据分布作为参考。**这与前端设置页的口径修正一致**。

### 12.4 图谱重建不幂等（幽灵数据）

**现象**：连续两次 `GET /graph?rebuild=true`，节点数不变但**边数持续增长**
（792 → 986）；且图上 `Trend` 节点有 **17 个**，而库里只有 **4 条**趋势。

**根因**：`build_from_signals()` 注释自称「幂等」，实际往**全局单例**图存储累加：

```python
store = get_graph_store()      # ← 全局单例，不清空
for sig in ...: store.add_node(...); store.add_edge(...)
```

`reset_graph_store()` 这个函数**存在但从未被调用**。于是每次重建都在旧图上叠加，
已删除的实体以幽灵节点形式残留，`blank_spots()` / `centrality()` 读到的是历史并集
而非当前状态。

**修复**：`build_from_signals()` 开头调用 `reset_graph_store()`，每次重建从空图开始。
新增测试 `test_build_from_signals_is_idempotent` 锁定（连续重建两次，节点与边数必须一致）。

> 📌 **通用教训**：「幂等」是**断言**，不是**注释**。凡是往全局单例里写入的
> `build_*` / `rebuild_*` 函数，都必须显式证明「连续调用两次结果相同」——
> 本项目已连续两次踩到该模式（`upsert_trends` 键不一致、此处图存储未重置）。
> 判据很简单：**连续调两次，比对结果**。

### 12.5 趋势 `industry` 全空 → 趋势名被当成赛道名

**现象**：`tracks` 表混进一条「AI算力硬件高精度光学检测」（desc 为空），
并在「空白点识别」里冒充赛道显示；4 条趋势的 `industry` **全部为 None**。

**根因链**：

1. LLM 路径的 prompt **不要求输出 `industry`** ⇒ `t.get("industry")` 为 None；
2. 两个落库入口中，`sync_analysis`（机会分析）**没传 `industry` 参数** ⇒ 兜底也失效；
3. `to_pool` 写的是 `resolve_track(db, trend.industry or trend.name)` ——
   **用趋势名兜底**，而 `resolve_track` 在赛道不存在时会**静默创建**一条 ⇒
   干净地造出一条名为趋势名的脏赛道。

**修复**（三处）：

| 位置 | 改动 |
| --- | --- |
| `upsert_trends` | industry 兜底链增加第三级：**从证据信号推断**（`_industry_from_evidence`，取众数） |
| `to_pool` | 去掉 `or trend.name` —— 无名可归时 `track_id` 留空，**不造假数据** |
| 数据 | 回填 4 条趋势 industry；删脏赛道；其引用（机会 1 + **预警 16**）改指 `AI+制造` |

> 📌 **通用教训**：**兜底值必须与被兜底的语义同质**。「趋势名」和「赛道名」
> 是完全不同的实体，用前者兜底后者必然造假。另外 `resolve_track` 这种
> 「查不到就静默创建」的写法会**掩盖**上游数据缺陷 —— 宁可留空并在日志里告警。
>
> 还有一个值得记的点：删除主表记录前必须枚举**所有**外键引用。
> 本次第一版清理脚本只修了 `opportunities`，结果被 `alerts.track_id`（16 行）
> 的外键约束打回、整笔事务回滚 —— 好在事务回滚保证了数据一致。
