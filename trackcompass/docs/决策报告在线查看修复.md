# 决策报告「不能在线看」修复

> **触发**：用户 2026-09-16 ——「决策报告不能在线看吗？」
> **结论**：是缺陷，已修。列表接口**不返回正文**，而前端把列表项直接塞进预览区
> ⇒ 每份历史报告都显示「该报告无正文内容」。已改为点「查看全文」时单独拉详情，
> 并补上「在线打开」（新标签页看排版版 HTML）。
> **改动面**：前端 1 个文件 + 冒烟脚本；**零后端改动**（详情接口本来就有正文，只是没人调）。

---

## 一、现象与根因

| 环节 | 实际情况 |
| --- | --- |
| 用户操作 | 在「报告列表」点**查看** |
| 前端原实现 | `onClick={() => setPreview(r)}` —— 直接把**列表项**当预览数据 |
| 列表接口 `GET /reports` | 只回元信息（title/version/format/evidence_count/page_count/created_at），**不含 `content`** |
| 渲染分支 | `preview.content?.sections?.length ? 章节渲染 : <Empty description="该报告无正文内容" />` |
| 结果 | 除「刚生成的那份」（POST 响应里带 `sections_detail`）之外，**所有历史报告都显示「该报告无正文内容」** |

另外发现一个隐患：导出接口返回的 `url` 是服务端本地路径 `file:///D:/...`，
**浏览器打不开**；真正的入口是后端挂载的 `/static/reports/<文件名>`
（前端原先把 `path` 取 basename 拼静态地址 —— 这条其实是对的，但 `url` 字段没人用，
容易误导后来者直接 `window.open(res.url)`）。

---

## 二、修法

1. **「查看全文」补一次详情请求**：`GET /reports/{id}` 本来就返回 `content`（含 9 段 markdown 与引用），
   前端 `reportApi.detail()` 也早就在客户端里 —— **只是没人调用**。
   - 刚生成的那份已带正文 ⇒ 直接用，省一次请求；
   - 历史报告 ⇒ 拉详情，期间标题区 loading。
2. **新增「在线打开」**：新标签页打开排版版 HTML。
   - 有导出产物 ⇒ 直接开 `/static/reports/<文件名>`；
   - 没导出过 ⇒ 先导 HTML 再开（导出接口返回值里的 `file://` URI 一律经
     `staticUrlOf()` 转成同端口静态地址）。
3. **列表动作重排**：`查看全文` / `在线打开` / `导出 ▾`（HTML·Markdown·PPT·Word·JSON 收进下拉，
   避免一行四个链接把列表撑乱）。
4. **预览区头部**加「在线打开」（主按钮）+ 保留 导出 PPT / Word。
5. **导出行为收敛**：导 HTML 顺手在新标签页打开；PPT/Word 属于「下载后编辑」，只提示文件已生成。

---

## 三、验证（实测）

| 项 | 结果 |
| --- | --- |
| 详情接口 | `GET /reports/{id}` → **9 个章节**，含 markdown 与引用（实测：执行摘要 191 字 / 赛道定义与市场空间 505 字 / 需求验证 446 字） |
| 静态产物 | `/static/reports/<文件名>.html` → **HTTP 200** |
| UI（真实 Chromium） | 见下 |

```
✅ 报告列表已渲染（10 份报告）
✅ ★ 点「查看全文」能在线看到报告正文（正文含「执行摘要」＝ true，且不再出现「该报告无正文内容」）
✅ 报告按 9 段结构渲染（命中 9/9）
✅ ★ 「在线打开」的静态地址可访问（HTTP 200）
```

UI 冒烟整体 **46/46**（在原有 42 项上新增 4 项报告场景）。
截图留档：`docs/决策报告-在线查看-验证.png`。

### 顺带修掉的一个真竞态（冒烟暴露）

首屏「默认数据源自动补全」与用户点击之间会打架：若用户在 `/signals` 返回**之前**点了「开始分析」，
补全逻辑随后把数据源从 5 类改成 8 类 ⇒ 刚出的结果立刻被判定为「检索条件已改动」。
现在**一开跑就视为用户已确定数据源**，补全逻辑不再改动条件。
（这条是冒烟偶发假失败牵出来的 —— 断言不稳有时真是产品问题，值得追。）
