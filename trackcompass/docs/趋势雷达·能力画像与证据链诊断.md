# 趋势雷达：能力画像交叉核对 与 证据链 诊断

> 起因：用户提问「能力画像 × 外部信号里有『智能体』，但 30 条趋势里没有，正常吗？」
> 实测日期 2026-09-14 | 结论先行 + 证据链

---

## 一、直接回答：正常，且是刻意设计

「智能体」出现在面板里但不在趋势里 —— **完全正常**，因为它被放进了**「情报空白」**区，而不是「已匹配」区。两者的语义边界是：

| 面板区块 | 含义 | 渲染 |
| --- | --- | --- |
| 已匹配（有外部信号支撑） | 该能力词**在信号库里能找到证据** | 金色 `⚑` 标签 |
| 情报空白（画像写了、外部零信号） | 画像提到但**外部证据为零** —— **不是趋势** | 普通标签 |

`frontend/src/pages/Trends.tsx:303-368` 的注释写得很直白：

> · `已匹配` —— 该能力有对应趋势（有外部信号支撑）
> · `情报空白` —— 画像写了、但外部零信号；**不是趋势**，是需要补数据源的地方

面板底部还有一条显式警示：**「它们不是趋势，而是情报空白 —— 建议补数据源或做定向调研，而不是据此决策。」**

### 判定逻辑（`backend/app/agents/trend.py:236-254`）

```python
def _capability_gaps(caps: list[str], covered: set[str]) -> list[dict]:
    covered_l = {str(c).lower() for c in covered if c}
    for c in caps:
        if any(cl in k or k in cl for k in covered_l):
            continue          # 有证据 → 不进缺口
        gaps.append({"name": c, "source": "capability_profile", "evidence_count": 0, ...})
```

`covered` = 信号关键词集合（`_covered_from_buckets`）+ 已匹配的能力词（LLM 路径在 `postprocess` 里重算，避免"既匹配又缺口"的自相矛盾）。

### 实测核对（40 条种子信号的 15 个关键词）

| 能力词（磅旗科技画像，共 7 个） | 信号关键词中出现 | 应入缺口 | 实际入缺口 |
| --- | --- | --- | --- |
| 计算机视觉 | ✅ 8 次 | 否 | 否 ✓ |
| 具身智能 | ✅ 4 次 | 否 | 否 ✓ |
| 大模型 | ❌ 0 次 | 是 | 是 ✓ |
| 智能体 | ❌ 0 次 | 是 | 是 ✓ |
| 强化学习 | ❌ 0 次 | 是 | 是 ✓ |
| 软件系统 | ❌ 0 次 | 是 | 是 ✓ |
| 工厂物流线 | ❌ 0 次 | 是 | 是 ✓ |

> ⚠️ 统计陷阱：`signals.keywords` 在 SQLite 里是 **JSON 转义存储**（`["\u8ba1\u7b97..."]`），
> 直接用 `LIKE '%计算机视觉%'` 会**误报 0 条**。必须 `json.loads()` 后再比对。

**本次扫描实测返回**（`POST /api/v1/trends/scan`）：

```json
"capability_terms":   ["计算机视觉","大模型","智能体","强化学习","具身智能","软件系统","工厂物流线"],
"capability_matched": [],
"capability_gaps":    ["大模型","智能体","强化学习","软件系统","工厂物流线"]
```

5 个零证据词一个不多一个不少 —— **缺口判定本身是正确的**。

### 根因：不是算法问题，是数据源问题

| 事实 | 数值 |
| --- | --- |
| 信号总数 | 40（全部为种子数据） |
| 信号里出现「智能体」 | **0 次**（标题 / 正文 / 关键词三路全零） |
| 信号里出现「大模型」 | **0 次** |
| 是否有网络采集器 | **无** —— 所有 `url` 均为 `example.com` 占位 |

趋势来自信号聚类，**没有信号就聚不出趋势**。想让「智能体」变成趋势，唯一路径是接入真实数据源。

## 二、三个容易造成困惑的表层因素（非缺陷，但影响理解）

### 1. 面板是**瞬态**的 —— 刷新即消失

```tsx
// Trends.tsx:44,150
const [scanResult, setScanResult] = useState<TrendScanResult | null>(null)
...
{scanResult ? <CapabilityPanel result={scanResult} /> : null}
```

面板数据来自**扫描接口的返回值**（`setScanResult(res)`），**不落库、不持久化**。只有点击「扫描」那一刻才渲染，刷新页面就没了。
而趋势列表是持久化的（读 `trends` 表）—— 两块的"存在感"因此完全不对等，**这是"没搞明白"的首要原因**。

### 2. 前端只显示 30 条

```tsx
// Trends.tsx:46-53
trendApi.list({ industry, direction, limit: 30 })
```

写死 `limit: 30`。DB 里实际有 **40 条**趋势（后端接口上限 100）。所以"30 条"是展示截断的结果，不是全部数据。

### 3. 「已匹配」与「情报空白」口径不同源

| 视图 | 数据来源 |
| --- | --- |
| 列表行的 `⚑` 标签 | **DB 里全部历史趋势**的 `factors._capability.matched` |
| 面板的「情报空白」 | **本次扫描**产出（`capability_gaps`） |

两者不是同一时点的同一份数据 → 会同时出现"某条趋势标着 ⚑大模型"和"大模型：情报空白"。**见下方 P2。**

## 三、顺带发现的三个真实缺陷（待裁决）

### P1 · 趋势证据链断裂（40/40 条，用户可见）

**现象**：点开任意趋势详情，「证据链」渲染出一排 **`—`**（无标题、无来源、无链接）。

**实测**：

```
趋势: 工业视觉与智能质检规模化落地 | 证据数: 3
详情 evidence 原始值: ["E1", "E3", "E4"]
→ 前端渲染：(e as Record).title ?? '—'  →  对字符串取 .title 得 undefined  →  显示 "—"
```

**根因**：LLM 路径的 prompt 要求编号形式（`backend/app/agents/trend.py:40`）：

```python
"\"confidence\":0.0,\"direction\":\"tailwind|headwind\",\"evidence\":[\"E1\"]}]}"
```

而落库时**直接存了 LLM 输出**（`backend/app/api/v1/opportunities.py:237`）：

```python
existing.evidence = t.get("evidence", [])   # ← 没有把 E1 映射回真实 signal_id
```

全库检索确认**不存在任何反向映射**（`startswith("E")` / `lstrip("E")` 均无命中）。

**对照**：规则路径本来是对的 —— 产出的是含真实 `signal_id` 的 dict 列表（`trend.py:75-80`）。**只有 LLM 路径丢了映射**，而当前线上走的就是 LLM 路径。

**影响面**：趋势页的"证据链"下钻、证据链完整率（`citation_ratio`）对趋势类证据均失真。

**修复方向（待确认）**：在 `postprocess` 内用当轮证据池（`_dedupe_evidence` 产出的 `ref` 列表）把 `E1` 反查替换为真实证据 dict；或改 prompt 让模型直接回 `signal_id`。

### P2 · 匹配口径不一致

同一页面可同时出现「⚑大模型（已匹配）」与「大模型（情报空白）」：

- `/api/v1/trends` 返回的 matched 全集 = `['大模型','强化学习']`（来自历史趋势 `factors._capability`）
- 本次 scan 的 `capability_gaps` 也含 `'大模型'`、`'强化学习'`

两者各自内部自洽（`postprocess` 已用 `covered = 信号关键词 ∪ matched` 重算缺口），但**跨接口未对齐**。

### P3 · 旧数据堆积（40 条趋势里大量近重复）

40 条趋势分 4 个批次落库（`04:00` 8 条 / `06:50` 4 条 / `08:5x` 13 条 / `09:0x` 15 条），同一主题反复累积：

| 同主题的不同趋势名 |
| --- |
| 工业视觉与智能质检规模化落地 / 工业视觉与智能质检 / 低成本快速部署的工业视觉质检解决方案 / 低成本快速部署的工业视觉质检方案 / 轻量化边缘AI质检系统 / 高鲁棒性工业质检算法优化 … |

**原因**：`persist_scan_result` 按 `Trend.name ==` **精确匹配**做 upsert，而 LLM 每次生成的名字都不同 → 每次都新建一条。

**影响**：雷达页被同义条目淹没；「⚑」标签出现在哪条上带有随机性。

## 四、结论汇总

| # | 问题 | 性质 | 优先级 |
| --- | --- | --- | --- |
| — | 「智能体」不在趋势里 | **正常，设计如此**（信号 0 证据 → 情报空白） | — |
| 1 | 面板瞬态、刷新即消失 | UX 设计问题 | P2 |
| 2 | 前端写死 30 条 | 展示截断 | P3 |
| 3 | 趋势证据链断裂（40/40） | **功能缺陷，用户可见** | **P1** |
| 4 | 已匹配 / 情报空白 跨接口口径不一致 | 数据一致性 | P2 |
| 5 | 趋势近重复堆积（同主题多条目） | 数据治理 | P2 |

**最该先修的是 #3**：它是唯一会让用户"点开看到空白"的功能性缺陷，且修复范围清晰（一处映射逻辑 + prompt 微调）。
