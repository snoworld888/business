# 赛道评分「排序对比」重复条目 —— 修复报告

> 执行日期 2026-09-14 | 用户反馈：「赛道评分，排序对比有重复内容」

---

## 一、现象

「赛道评分」页的**排序对比**（`Scorecard.tsx:289`）里出现大量完全相同的条目：

```
机会总数: 25
重复标题: {'AI 质检商业化': 25}      ← 25 条全部同名
唯一标题数: 1
```

---

## 二、根因（两个因素叠加）

### 1. `to-pool` 没有幂等 —— 同一趋势可反复建卡

`app/api/v1/trends.py::to_pool()` 每次调用都无条件新建：

```python
opp = Opportunity(...)          # ← 每次都新建
db.add(opp)
trend.in_pool = True            # ← 设了标记，却从不据它防重
```

实测该接口被反复调用后，**同一趋势累积出 17 条同名机会**：

| source_trend_id | 累积条数 |
| --- | --- |
| `38601ce3-f461-…` | 17 条 |
| `bc6b3c49-b83c-…` | 8 条 |

创建时间横跨 04:00 → 09:51（每一次 E2E / 手动测试各留一条）。

### 2. E2E 冒烟脚本写死了标题

```python
pool = data(CLIENT.post(f"/trends/{trends[0]['id']}/to-pool",
                        json={"title": "AI 质检商业化"}))    # ← 固定标题
```

即使来源是**不同趋势**，卡片标题也全部相同 ⇒ 视觉上完全无法区分。
（正常留空时标题取趋势名，天然唯一。）

---

## 三、修复

### 1. `to-pool` 幂等

```python
existing = db.scalar(
    select(Opportunity).where(Opportunity.tenant_id == tid,
                              Opportunity.source_trend_id == trend.id)
    .order_by(Opportunity.created_at)
)
if existing is not None:
    if not trend.in_pool:
        trend.in_pool = True
        db.commit()
    return ok({"opportunity_id": existing.id, "title": existing.title,
               "status": existing.status, "reused": True},
              message="该趋势已在机会池中，返回既有卡片")
```

语义：**一条趋势 ⇄ 一张机会卡**。重复入池返回既有卡片，并带 `reused: True` 供前端提示。

**验证**（对同一趋势连续入池 3 次）：

```
第1次: id=92a69a73 reused=True
第2次: id=92a69a73 reused=True
第3次: id=92a69a73 reused=True
→ 三次 id 一致: True
→ 入池 3 次后机会总数: 2（未新增）
```

### 2. E2E 脚本不再写死标题

```python
pool = data(CLIENT.post(f"/trends/{trends[0]['id']}/to-pool", json={}))
```

留空即用趋势名，天然唯一。同时断言放宽（幂等后可能复用状态已流转的卡片）：

```python
check("趋势 → 机会卡片", bool(opp_id), f"opp={opp_id[:8]} status={pool['status']}")
```

### 3. 既有测试同步调整

`test_trend_to_pool_creates_opportunity` 原先强断言 `status == "screening"`，
幂等后复用既有卡片时状态可能已是 `verifying` ⇒ 改为断言 `in ("screening", "verifying")`，
并**新增幂等断言**（重复调用必须返回同一 id + `reused=True`）。

## 七、说明与建议

1. **现在排序对比只有 2 条** —— 这是"每个趋势保留 1 条"的结果，不是功能异常。
   如需更丰富的对比样本，可在**趋势雷达**页把其他趋势「加入机会池」——
   已有幂等保护，重复点击不会再产生重复卡片。
2. **同类风险提醒**：任何"创建型"接口都应默认考虑幂等。本次与上一轮的
   `persist_scan_result`/`upsert_trends` 是同一类问题（重复写入），
   根因都是**只写入、不防重**。
3. **E2E 脚本的数据污染**值得关注：它会向真实库写数据。
   本次靠"幂等 + 不写死标题"让它不再累积；若后续要彻底隔离，
   建议 E2E 使用独立的测试租户或跑在临时库上。
