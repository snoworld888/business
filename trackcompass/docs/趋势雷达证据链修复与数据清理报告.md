## 二、P1 修复：趋势证据链断裂

### 根因

LLM 路径的 prompt 要求模型回**编号**（`trend.py:40`）：

```python
"\"confidence\":0.0,\"direction\":\"tailwind|headwind\",\"evidence\":[\"E1\"]}]}"
```

而落库时**直接存了模型原始输出**，两处都是：

```python
existing.evidence = t.get("evidence", [])   # analysis.py:172 / opportunities.py:237
```

全库检索确认**不存在任何反向映射**（`startswith("E")` / `lstrip("E")` 均无命中）。
⇒ `trends.evidence` 存的是 `["E1","E3","E4"]`
⇒ 前端 `Trends.tsx` 取 `e.title` / `e.source` / `e.url` 全部落空
⇒ 证据链渲染成一排 `—`。

> 对照：**规则路径本来是对的** —— 它产出含真实 `signal_id` 的 dict 列表（`trend.py:75-80`）。
> 只有 LLM 路径丢了映射，而线上走的正是 LLM 路径。

### 方案

**关键设计点：映射表不能是 `state.evidence`。**

| 候选 | 问题 |
| --- | --- |
| `state.evidence` 的 `ref` | ① 跨 Agent 累积，编号被 `len()+1` 续写；② 第 1 层 `[TrendReconAgent(), DemandDiscoveryAgent()]` 是**并行**执行的，两边 append 交错；③ `_dedupe_evidence` 在最后才统一重排 |

只有 **Agent 自己刚检索的那批 docs**，其顺序才与 prompt 里的 `[E{i}]` 严格一致
（`build_context` 与无 RAG 分支都是 `enumerate(docs, start=1)`）。

因此：

1. `app/agents/base.py::retrieve()` 记录 `self._retrieved_docs = list(docs)`
2. 新增 `BaseAgent.resolve_evidence_refs(items)`：
   - `dict` **原样透传**（规则路径 / 已是完整证据）
   - 字符串编号 → 按本次检索顺序反查（`e1` / `" E2 "` 也能命中）
   - **反查不到的一律丢弃** —— 模型可能编出不存在的编号，宁可少一条，也不让前端渲染空条目
3. `app/agents/trend.py::postprocess()` 对每个 trend 调 `self.resolve_evidence_refs(...)`

两处落库点**无需改动** —— 它们只存 agent 输出的 `evidence`，修复在源头完成。

### 验证

修复后重扫，证据链实测：

```
趋势: 工业视觉与数字孪生规模化应用
   ✅ title='某工业软件集团设立 20 亿元智能制造产业基金'
      source='产业投资快讯' | url='https://example.com/signal/fe3aa04111...' | ref=E1
   ✅ title='《制造业数字化转型行动方案》发布'
      source='工业和信息化部' | url='https://example.com/signal/53fcc3500226...' | ref=E5
```

`ref=E1…E6` 是本次检索的编号（`top_k=6`），映射正确。

## 三、P3 清理：40 条趋势 → 12 条

### 依赖检查（清理前必做）

`opportunities.source_trend_id` 有 **22 条非空且全部有效** —— 不能直接清空趋势。

| 分类 | 数量 | 处理 |
| --- | --- | --- |
| 被机会卡片引用 | 2 条 | **保留**（保护溯源链） |
| 未被引用 | 38 条 | 删除 |

### 备份（红线）

```
backend/db_backup/2026-09-14_trend-cleanup/trackcompass.db   (2232 KB)
  trends 40 条 / signals 40 条 / opportunities 22 条
```

使用 SQLite 在线 backup API（`src.backup(dst)`），保证事务一致，非文件拷贝。

### 对被保留的 2 条旧趋势

它们的证据同样是编号串、**无法可靠回溯**（原始检索上下文已丢失）。处理：

1. 先置空 `evidence`，原编号存入内部键 `factors._legacy_evidence_refs`（可追溯，接口层过滤 `_` 前缀）
2. 再按「趋势名/描述命中的信号关键词」**回填真实证据**，并标注 `backfilled: true`
   （这是**按事实关联**：证据本身是信号库里真实存在的信号，关联依据是关键词命中，非推测）

> 说明：这一步是必要的 —— 它们被机会卡片引用，属活跃数据；
> 留空会让用户点进去看到"无证据"，而它们的证据链实际是可重建的。

## 四、防复发：统一两处落库

抽出 `app/services/analysis.py::upsert_trends()`，两个入口共用：

```python
def upsert_trends(db, tenant_id, trends, industry=None, limit=None) -> int:
    """趋势落库（幂等 upsert），所有入口必须共用这一份实现。"""
```

修复前两处各写各的：

| 入口 | 原匹配键 |
| --- | --- |
| `sync_analysis`（机会分析） | `name + industry` |
| `persist_scan_result`（雷达扫描） | `tenant_id + name` |

同一主题从两个入口进来会各自建一条 ⇒ 堆积。统一为 `tenant_id + name`。

同时统一了 `_capability`（能力画像匹配）的写入 —— 此前**只有扫描入口写**，机会分析入口不写，导致列表页 `⚑` 标签时有时无。

### 幂等性验证

连续 2 次补扫，`trends` 总数**保持不变**（同名命中 upsert 更新，不新增）：

```
第 1 次补扫: 生成 4 条 | top1 = 工业视觉与数字孪生规模化应用
第 2 次补扫: 生成 4 条 | top1 = 工业视觉与数字孪生规模化应用
```

## 五、测试加强

`scripts/e2e_smoke.py` 的「趋势含证据链」此前是 `all(t["evidence"] for t in trends[:3])`
—— **只判非空**，所以编号串也能"通过"。已改为校验**可渲染性**：

```python
def _renderable(t):
    ev = t.get("evidence") or []
    return bool(ev) and all(
        isinstance(e, dict) and e.get("signal_id") and e.get("title") for e in ev)
check("趋势含证据链（可渲染）", all(_renderable(t) for t in trends[:3]), ...)
```

`tests/test_agents.py` 新增 `TestEvidenceRefResolution`（9 项）：编号反查、大小写/空白容错、未知编号丢弃、dict 透传、空输入、未检索时不抛错、postprocess 端到端、规则路径不被破坏、`_retrieved_docs` 不跨调用残留。

### 本轮踩到的流程性问题（供后续参考）

1. **`state.evidence` 不可作映射表** —— 跨 Agent 累积 + 第 1 层并行交错，编号会错位
2. **E2E 弱检查会掩盖缺陷** —— "非空"不等于"可用"，修复前该检查一直假通过
3. **SQLite 里 `keywords` 是 JSON 转义中文** —— `LIKE '%计算机视觉%'` 误报 0 条，必须 `json.loads()` 后比对
4. **`.env` 改动不自动生效** —— 引擎在 `_build_rag()` 实例化时读取；且旧进程非 `--reload` 模式，必须硬重启
5. **Git Bash 下 `curl -o /dev/null` 返回 exit 23** —— 会把 `&&` 链截断，导致后续命令静默不执行
