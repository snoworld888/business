## 四之二、专项：控制台 404 问题的定位与根治

**现象**：用户报告「Failed to load resource: the server responded with a status of 404 (Not Found)」。

**定位过程**（结论先行，逐步排除）：

| 步骤 | 怀疑对象 | 检查手段 | 结果 |
| --- | --- | --- | --- |
| 1 | 服务是否挂了 | 探测 5180 / 8020 | 均为 200，服务正常 |
| 2 | 是否 API 路径写错 | `scripts/check_api_contract.py` 交叉比对前端 55 个调用路径与后端 59 条路由 | **55/55 全部匹配**，API 无问题 |
| 3 | 是否静态资源缺失 | 逐个探测 `/`、`/assets/*.js`、`/assets/*.css` | 均 200 |
| 4 | 浏览器默认请求 | 探测 `/favicon.ico` | **404 ← 命中** |

**根因**：`index.html` 未声明图标，浏览器自动请求 `/favicon.ico`，服务端未提供 → 控制台报 404。
功能无影响，但属于「噪声告警」，会让使用者误判系统有故障。

**根治措施（三层）**：

1. 新增 `frontend/public/favicon.svg`（品牌罗盘图标），并在 `index.html` 声明
   `<link rel="icon" type="image/svg+xml" href="/favicon.svg" />`，浏览器不再请求 `/favicon.ico`。
2. 后端新增 `/favicon.ico` 兜底路由：存在图标则返回 SVG，否则返回 **204**，**保证永不 404**。
3. 新增 `scripts/check_api_contract.py`，把「前端调用路径 vs 后端路由」的一致性检查固化为可重复执行的脚本。

**回归用例**：`test_favicon_never_404`（断言状态码 ∈ {200, 204}）、
`test_frontend_assets_served`（断言 index.html 引用的每个 `/assets/*` 均可取）、
`test_root_json_fallback`（断言 dist 缺失时回退 JSON 而非 404）。

**附带改进：改为单端口托管**。原先 UI 依赖 Vite dev server + proxy 转发，
链路长、易受进程生命周期影响。现由后端在 `/` 直接托管 `frontend/dist`
（`SERVE_FRONTEND=true`，默认开启），**一个进程、一个端口**同时提供 UI 与 API。
前端使用 HashRouter，因此无需服务端 history fallback。

**⚠️ FastAPI 路由顺序陷阱（已写入代码注释）**：`app.mount("/", StaticFiles(...))`
会匹配所有路径，因此显式的 `/` 与 `/favicon.ico` 路由**必须注册在 mount 之前**，
否则会被 StaticFiles 抢先匹配，favicon 仍然 404。
