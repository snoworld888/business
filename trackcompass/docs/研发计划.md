## 一、结论先行

四份文档给出的蓝图完整，但技术选型（Kafka / Neo4j / Milvus / K8s / ClickHouse）在单机开发环境无法直接落地。

> **保留全部领域契约与七 Agent 架构，把重型基础设施做成「开关 + 适配器」**——
> 未配置任何中间件即可跑通端到端工作流，配置后业务代码零改动。

## 三、关键技术决策与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| Agent 实现方式 | 每个 Agent 同时提供 `rule()` 与 `build_prompt()` | `rule()` 保证离线可跑、可断言、可回归；切真实 LLM 后规则实现降级为校验基线，**换模型不改业务** |
| 向量与图谱 | 默认内存实现 + 生产适配器 | 开发机无需 Milvus/Neo4j 即可验证检索与图算法；生产切换零业务改动 |
| 确定性 Embedding | 字符 n-gram 哈希投影（1536 维） | 同文本恒得同向量，便于断言与回归；语义能力弱但流程完整，生产切 BGE-M3 |
| 评分类结构与文档公式 | 逐条对齐技术文档 §4.2/§4.4/§4.5 原文公式 | 单测直接断言公式等价，避免"实现漂移" |
| 反馈循环 | 决策判定 verify/watch 且存在冲突点时回灌重跑 | 实现技术文档 §5.1 的反馈边语义，用「有界循环」防止无限迭代 |
| 口令散列 | 标准库 `pbkdf2_hmac`（12 万轮） | 避免 passlib/bcrypt 在新版 Python 的兼容问题，零二进制依赖 |
| 前端状态管理 | Hooks + `useAsync`，不引入 Redux | 页面级数据独立，避免过度设计；契约来自后端，前端只做展示与下钻 |

## 四、已知限制与风险

| 风险 | 影响 | 当前处置 |
| --- | --- | --- |
| 规则引擎的语义精度 | 痛点聚类依赖词典与关键词，召回/准确低于 BERT+HDBSCAN | 接口与输出结构已定型，P2-5 换真实模型即可提升，无需改动上层 |
| 种子数据规模 | 40 条信号，趋势/图谱规模有限 | P2-1 接入真实采集器；算法与可视化已验证可支撑更大规模 |
| 内存向量库不持久 | 后端重启后需重建索引 | 首次分析自动触发重建；P2-2/P2-3 切 pgvector/Milvus 后根治 |
| 需求探针同步执行 | 大数据量下请求耗时上升 | P2-4 改异步任务 |
| 报告 PPTX/DOCX | 未安装可选依赖时降级为 Markdown | 已在 `requirements.txt` 注释中给出依赖，安装即启用 |
| 单机端口冲突 | 8010 已被本机其他服务占用 | 统一改用 **8020**，并在脚本与文档中固化 |

## 五、下一步建议顺序

1. **P2-1 真实数据源接入**（最高价值）——只有真实信号才能暴露算法与评分口径的真实缺陷。
2. **P2-5 真实 LLM 接入**——先把 7 个 Prompt 的产出质量调优，规则实现作为回归基线。
3. **P2-2/P2-3 存储切换**——数据量上来后再切，避免过早引入运维负担。
4. **P2-10 前端 E2E**——补 Playwright，把 30 项 HTTP 冒烟升级为浏览器级验证。
