## 二、问题 1：需求探针整页白屏（P0）

### 报错

```
Uncaught TypeError: Cannot read properties of undefined (reading 'map')
  at Demand.tsx:194:40          ← {p.experiments.map((m) => ...)}
```

### 根因

LLM 路径的 prompt **没有要求**模型输出 `experiments`（`demand.py:55-56`）：

```python
"{\"pain_points\":[{\"name\":\"\",\"freq\":0,\"sentiment\":-0.5,"
"\"demand_score\":0.0,\"samples\":[]}],\"suggested_experiments\":[]}"
```

而 `postprocess` 只补了 `demand_score` / `samples` / `ref`：

```python
p.setdefault("samples", [])
```

⇒ LLM 路径下 `pain_points[].experiments` **缺失** ⇒ 前端 `p.experiments.map()` 抛错 ⇒ 整页白屏。

（规则路径有该字段 —— `EXPERIMENT_RECOMMEND.get(name, ...)`，所以规则模式下不复现。）

### 修复

**后端**（源头修复，`demand.py::postprocess`）：按规则路径同样的算法补齐，并兼容模型返回字符串：

```python
p["experiments"] = as_list(p.get("experiments")) or \
    EXPERIMENT_RECOMMEND.get(str(p.get("name") or ""), ["客户访谈", "问卷调研"])
```

**前端**（防御，避免同类问题再次白屏）：`(p.experiments ?? []).map(...)`、`(p.samples ?? []).map(...)`

### 验证

```
痛点 3 类 | experiments 非数组: 0 个
样例: 识别准确率不足与高误检/漏检率 → ['客户访谈', '问卷调研']
```

## 三、问题 2：知识图谱的"非文字字符串"

### 根因

`graph.py::to_cytoscape()` 把节点的 `key` 直接当显示名：

```python
{"data": {"id": n, "label": d.get("key"), "type": d.get("label"), ...}}
```

而 `key` 的取值是 **UUID**（Signal / Opportunity），真正可读的名字在 `title` 属性里：

```
[Signal]      label: "228439ca-e47a-4331-88dc-6f47df67e491"   ← 40 个
[Opportunity] label: "7e83dd99-11fc-4d2c-9b86-10c8cab8e06c"   ← 24 个
[Track]       label: "AI+制造"    ✅ 本来就可读（key 就是名字）
```

**合计 64 个节点显示 UUID**。`Opportunity` 的 `TYPE_SIZE=26 ≥ 18`，所以其标签**直接画在图上** —— 这就是用户看到的"很多非文字字符串"。
另外 `centrality()` 的 `name` 同样是 key，前端「中心性排名」表直接渲染 ⇒ 表里也是 UUID。

### 修复

**后端** —— 显示名优先取可读字段，并补回被丢掉的 `key`（原实现把 `key` 并进 props 又被 exclude，前端无法下钻）：

```python
"label": d.get("title") or d.get("name") or d.get("key"),
"type": d.get("label"),
"key": d.get("key"),
```

`centrality()` 同样改为 `title or key`，并保留 `key` 字段。

**前端** —— 边关系名中文化（原样显示 `IMPACTS` / `BELONGS_TO` / `CONTAINS`）：

```ts
const REL_LABEL = { IMPACTS: '影响', BELONGS_TO: '属于', CONTAINS: '包含' }
```

### 验证

```
节点 114 | label 为 UUID 的: 0
[Signal]      label='《制造业数字化转型行动方案》发布'
[Opportunity] label='AI 质检商业化'
[Technology]  label='计算机视觉'   [Track] label='AI+制造'
中心性 top3: ['AI+制造', '智能质检', '计算机视觉']
```

## 四、问题 3：能力匹配漏项

### 根因

匹配池 `_capability_pool()` 只取**趋势自身**的字段（name / description / keywords），
而 **LLM 路径的 prompt 不要求输出 `keywords`** ⇒ 池子里几乎只有趋势名。

于是出现「画像写『计算机视觉』、趋势名写『工业视觉』」的字面不一致 ——
`_match_capabilities` 是**双向整串子串**匹配，无法命中：

```python
if any(cl in p or p in cl for p in pool_l):   # "计算机视觉" ⊄ "工业视觉与数字孪生规模化应用"
```

而**证据信号的关键词里明确就有「计算机视觉」**（种子数据 8 条信号带该词）—— 这份最可靠的证据被排除在比对之外。

### 实测漏项（修复前）

| 趋势名 | 当前匹配 | 证据信号关键词里实际有 |
| --- | --- | --- |
| 工业视觉与智能质检规模化落地 | `[]` | **计算机视觉** ← 漏 |
| 工业视觉与数字孪生规模化应用 | `[]` | **计算机视觉** ← 漏 |
| 工业视觉与智能质检的鲁棒性优化 | `[]` | **计算机视觉** ← 漏 |
| 轻量化边缘AI质检与快速部署方案 | `[]` | **计算机视觉** ← 漏 |
| 轻量化预测性维护时序模型 | `[]` | **计算机视觉** ← 漏 |
| 智能质检 | `[]` | **计算机视觉** ← 漏 |
| 人形机器人核心零部件与整机量产 | `['具身智能']` | 具身智能 ✅ |

**7 条应匹配的趋势全部漏判。**

### 修复

比对池加入**证据信号的关键词**（这是事实，不是推测 —— 能力词确实存在于真实证据里）：

```python
def _capability_pool(trend, signals_by_id=None):
    pool = [name, description] + trend.keywords
    if signals_by_id:
        for e in (trend.get("evidence") or []):
            sig = signals_by_id.get(e.get("signal_id"))     # 按证据链反查
            pool += sig.keywords
```

`postprocess` 里构造 `signals_by_id = {s.id: s for s in state.signals}` 传入。

### 验证

```
已匹配: ['具身智能', '计算机视觉']        ← 修复前只有 ['具身智能']
情报空白: ['大模型', '智能体', '强化学习', '软件系统', '工厂物流线']   ← 未受影响
```

自洽约束仍成立：匹配上的词不会同时出现在「情报空白」里。

## 五、附带发现（#4）：图谱把趋势当成了赛道

`build_from_signals()`：

```python
for tr in db.query(Trend).all():
    store.add_node("Track", tr.name, ...)     # ← 趋势名被建成了 Track
```

`blank_spots()` 只筛 `label == "Track"` ⇒ 「空白点识别」返回趋势名，
而前端该表的列名是**「赛道」**：

```
修复前 空白点: ['智能质检', '工业视觉与智能质检规模化落地', '工业视觉与数字孪生规模化应用']
```

### 修复

趋势独立为 `Trend` 节点，并连到所属赛道：

```python
store.add_node("Trend", tr.name, industry=tr.industry, score=tr.score)
if tr.industry:
    store.add_node("Track", tr.industry, industry=tr.industry)
    store.add_edge("Track", tr.industry, "HAS_TREND", "Trend", tr.name)
```

前端补 `Trend` 的颜色 / 尺寸。

### 验证（节点类型分布）

| 类型 | 修复前 | 修复后 |
| --- | --- | --- |
| **Track** | **16**（4 真赛道 + 12 趋势名） | **4**（只剩真赛道）✅ |
| **Trend** | — | **14** ✅ |
| Signal / Opportunity / Technology / … | 不变 | 不变 |

> ⚠️ **行为变化提示**：空白点数量由 12 → **0**。这是**语义修正后的正确结果** ——
> 4 条真赛道的连接度都 ≥ 阈值 5，确实不存在稀疏赛道。
> 修复前的"12 个空白点"其实是 12 个趋势名在冒充赛道。

## 八、流程发现

1. **"契约字段缺失"的典型模式**：prompt 没要求 → 后处理没兜 → 前端无防御 ⇒ 三层同时漏掉就白屏。
   三处任一层补上都能避免，本次**三层都补**（后端补源头、前端加防御）。
2. **弱检查比没有检查更危险**：E2E 此前只断言"趋势 evidence 非空"，编号串照样通过（见上一份报告）。
   本次新增的断言都校验**语义**而非存在性（如"label 不能是 UUID"、"experiments 必须是数组"）。
3. **`key` 与"显示名"必须分开**：UUID 型主键不能直接进 UI。图谱、中心性表两处同源缺陷。
4. **证据链是能力匹配的可靠来源**：趋势名是 LLM 自由文本（措辞漂移），信号关键词才是稳定事实。
