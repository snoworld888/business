# 趋势标签化重构：能力匹配从「落库快照」改为「查询时计算」

> 实施日期 2026-09-15 | 起因：用户提出「趋势记录应该有针对的标签，公司里拥有标签，就带出趋势」

---

## 一、原方案的缺陷

能力匹配原先这样实现：落库那一刻，用「当时的当前公司」算好 `matched`，把结果冻结进 `factors._capability`。

| 缺陷 | 后果 |
| --- | --- |
| **没记录是给哪家公司算的** | 切换公司后标注失效，可能出现"匹配的词不属于当前公司" |
| **是快照不是计算** | 每次修匹配逻辑都必须**回算全库历史数据**（实测有 5 条趋势的标注一直停在旧逻辑上） |
| 匹配结果不可追溯 | 无法回答"这条趋势为什么匹配给我" |

---

## 二、用户的方案 —— 正确且更优

```
趋势 ── 固有标签（客观属性，与公司无关）
公司 ── 能力词（主观能力）
匹配 = 查询时取交集 ⇒ 换公司即时重算，天然多公司隔离
```

**关键转变：匹配从「存储的快照」变成「查询的计算」。**

### 边界说明（重要）

这样改**不会**让"公司标签去生成趋势"。雷达始终是**外部信号**聚出来的客观趋势，
画像是**公司自己说的**能力。本次只是把"两者的关系"变成实时计算，没有让公司自说自话 ——
面板上那句"情报空白不是趋势"的警示依然成立。

---

## 三、实现

| 环节 | 改动 |
| --- | --- |
| `agents/trend.py` | 新增 `trend_tags(trend, signals_by_id)` —— 算趋势**客观标签**<br>标签来源：① 证据链各信号的关键词 ② 趋势名/描述命中 `TECH_VOCAB` 的词<br>导出公开别名 `match_capabilities`（供接口层调用） |

| `api/v1/trends.py` | 列表 / 详情两个接口改为**实时算**：`matched = 当前公司能力词 ∩ _tags` |

## 四、验证：同一趋势 × 不同公司 = 不同结论

这是本次改造的核心验收点。两家公司（**磅旗科技** / **智造未来科技**）对同一批 38 条趋势：

```
磅旗科技     能力词 = ['计算机视觉','大模型','智能体','强化学习','具身智能','软件系统','工厂物流线','工厂物流','多设备调度']
智造未来科技  能力词 = ['计算机视觉','深度学习','边缘计算','小样本工业缺陷识别模型训练方法']
```

**结论不同的趋势共 16 / 38 条**：

| 趋势 | 磅旗科技 | 智造未来科技 |
| --- | --- | --- |
| 工业视觉大模型与高精度质检算法 | `['计算机视觉','大模型']` | `['计算机视觉']` |
| 轻量化边缘AI质检与实时缺陷检测 | `['计算机视觉']` | `['计算机视觉','边缘计算']` |
| 人形机器人整机与核心零部件 | `['具身智能']` | `[]` |
| 基于时序大模型的预测性维护落地 | `['大模型']` | `[]` |
| 低成本基层医疗影像辅助诊断系统 | `[]` | `['深度学习']` |

⇒ **切换公司即时生效，且不再需要任何回算**。

## 五、连带修复的两个缺陷

### 1. 证据编号污染趋势标签

回填标签时实测发现：

```
工业视觉与智能质检规模化落地  tags=['计算机视觉','智能质检','工业互联网','预测性维护','E3','E4','E1']
                                                                                          ↑ 污染
```

根因：LLM 生成的趋势 `description` **会引用证据编号** ——
「结合政策补贴（**E3, E4**）与产业基金重点投向（**E1**），工业视觉技术将…」，
而 `extract_tech_keywords` 的英文提取条件 `len(mapped) > 1 and mapped.isascii()` 把 `E3`/`E4`/`E1` 当成了英文技术词。

**修复**：新增 `_ASCII_CODE_REF = re.compile(r"^[A-Za-z]\d+$")`，排除"单字母 + 数字"的编号串。

验证：

| 输入 | 输出 |
| --- | --- |
| 含 `E3, E4, E1` 的描述 | `['智能质检']` ✅ 编号被过滤 |
| `基于 YOLO 与 TensorFlow 的缺陷检测` | `['YOLO','TensorFlow']` ✅ 真词保留 |
| `面向 6G 与 AI 的智能体平台` | `['6G','智能体','人工智能']` ✅ 别名映射正常 |

回填后 **38 条趋势中仍含编号串的：0 条**。

### 2. 抽词碎片（同批发现）

`extract_tech_keywords` 的兜底用固定 4 字窗口切分（`[\u4e00-\u9fff]{2,4}`），
不管词边界 ⇒ 专利标题被切成 `小样本工` / `业缺陷识` / `别模型训` 等碎片。
已移除该兜底（调用方本就有 `or [text]`）。

## 附：关于「40 条种子信号」—— 真实数据应该怎么获取

### 现状

| 事实 | 证据 |
| --- | --- |
| 全仓库**0 行抓取代码** | 搜 `scrapy/playwright/selenium/BeautifulSoup/urlopen/aiohttp` —— 0 命中 |
| 40 条信号是**硬编码演示数据** | `app/seed/__init__.py::RAW_SIGNALS`，文件头注明"用于验证全链路" |
| URL 全是占位地址 | 40 条信号的 `url` 全部是 `https://example.com/signal/<md5>` |

### 系统留的口

`POST /api/v1/signals` —— 标注为「**写入信号（人工上传 / 外部采集器回传）**」。
即架构上采集器是**独立部署**的，跑完把标准化结果回传即可，**不需要改这个系统**。

### 技术文档 §3.1 已定义的正确方式

| 数据类型 | 来源 | 采集方式 | 频率 |
| --- | --- | --- | --- |
| 政策 | 政府网站、产业政策 | 爬虫 + API | 每日 |
| 技术 | 论文、专利 | API（Google Patents / **arXiv**） | 每日 |
| 资本 | 融资事件、财报 | API（Crunchbase / 企查查） | 每日 |
| 人才 | 招聘 JD | 爬虫 | 每日 |
| 市场 | 招标、应用商店评论 | 爬虫 + API | 每日 |
| 社媒 | 抖音、小红书、TikTok | API + 爬虫 | 实时/小时 |
| 供应链 | 企业公告、行业数据库 | API | 每周 |

设计链路：`数据源 → 采集器 → Kafka → 清洗/标准化 → 实体抽取 → …`
技术选型：Python Scrapy / Playwright / 官方 API SDK。

### 落地建议（按成本从低到高）

| 阶段 | 做法 | 说明 |
| --- | --- | --- |
| **P0 最快见效** | **arXiv API** + **政策 RSS** | arXiv 有官方免费 API、无需 key；政府网站多有 RSS/列表页。**优先做这两类**，当天就能有真实信号 |
| P1 | 官方 API（企查查 / 天眼查 / 招标网） | 需账号与授权，字段质量高 |
| P2 | Playwright 合规爬虫 | 覆盖招聘、社媒等无 API 的源 |
| P3 | Kafka 流水线 | 技术文档的完整形态，量级上来后再上 |

**关键**：这些都是往 `POST /signals` 回传，**本系统零改动**。
