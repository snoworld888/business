# 模型调用路径与本地显存评估

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.0 |
| 日期 | 2026-09-14 |
| 评估问题 | 「把 TrackCompass 所有模型调用改走 Hermes 服务，以减少本地显存挤占」 |
| 结论 | **❌ 该方案达不到目的 —— 走 Hermes 不省显存，反而更费显存。** 已定位真正的显存大户与 3 条可行替代方案 |
| 判定依据 | 全部为运行时与配置实测，见 §2 |

## 一、结论先行

| 问题 | 答案 |
| --- | --- |
| 系统内有几处调用模型？ | **2 个漏斗**：`agents/base.py:114`（LLM，7 个 Agent 共用）+ `embeddings.py`（向量化）。**无绕过点** |
| 这些调用目前落点在哪？ | **本机 → 零外部推理**。`LLM_PROVIDER=rule`（纯算法）；Embedding 用 `local` 哈希实现 |
| Hermes 的模型跑在哪？ | **本机 WSL 的 Ollama**（`http://localhost:11434/v1`，模型 `qwen3.8:27b`） |
| 改走 Hermes 能省显存吗？ | **不能。同一台机器、同一块 RTX 5090、同一个 Ollama 实例** |
| 反而有什么代价？ | Hermes 用 **128K 上下文**（`num_ctx=131072`），而 TrackCompass 的 prompt 只有几百~几千 token → **KV cache 显著放大，显存占用上升** |

> **一句话：把请求在本机内部转一圈，推理落点没有改变。
> TrackCompass 现在占用 0 显存；当前的显存压力来自 Hermes 自己（qwen3.8:27b @ 128K）。**

## 二、取证过程（每一条都有实测）

### 2.1 `192.168.2.192` 就是本机，不是远端

```
本机访问 192.168.2.192 时的源 IP : 192.168.2.192   ← 源 = 目标 ⇒ 本地地址
以太网适配器 以太网        : IPv4 = 192.168.2.192
以太网适配器 vEthernet(WSL): IPv4 = 172.25.240.1   （WSL 网关）
主机名                    : DESKTOP-9HDUO7P
```

**修正一条历史认知**：本机 LAN IP 是 **192.168.2.192**（此前记为 `192.168.2.28`，已过期）。
WSL 客户机 IP = **172.25.252.110**（此条正确），其网关为 `172.25.240.1`。

### 2.2 Hermes 跑在本机 WSL，PID 589

```
ss -ltnp | grep 9219
LISTEN 0 2048 0.0.0.0:9219 0.0.0.0:*  users:(("hermes",pid=589,fd=8))

/proc/589/cmdline → /home/pc/venvs/hermes-main/bin/hermes serve --host 0.0.0.0 --port 9219 --isolated
```

> ⚠️ **一个易踩的坑**：`systemctl --user is-active hermes-native-serve.service` 在
> root 上下文执行时返回 `inactive` / `Unit could not be found`，**是假阴性** ——
> 该 unit 属于 `pc` 用户。判服务存活请用 `ss -ltnp` 或 procfs，不要只信 `systemctl --user`。
>
> 顺带发现 WSL 内另有多个 Hermes 进程：PID 585/587（`--profile bot1 gateway run`）、
> 882533（`bot2`）、以及 2 个 `hermes_kernel_runner.py`。

### 2.3 Hermes 的模型 = 本机 Ollama（决定性证据）

`/home/pc/.hermes-agent-main/config.yaml`：

```yaml
custom_providers:
  - name: Local (localhost:11434)
    base_url: http://localhost:11434/v1      # ← 本机 WSL 的 Ollama
    model: qwen3.8:27b                       # ← 17.74 GB 本地权重
    models: [hermes3:8b, qwen3.8:27b, qwen3.6:35b-a3b, qwen3.6:27b,
             qwen2.5:7b, bge-m3:latest, glm-5.1:cloud, qwen2.5-coder:32b, qwen3.5:35b]
```

`/home/pc/.hermes-agent-main/cache/local_endpoint_probes.json`：

```json
{"server_type:http://127.0.0.1:11434": "ollama",
 "ollama_num_ctx:http://127.0.0.1:11434|qwen3.8:27b": 131072}
```

**两个关键事实**：
1. Hermes 的推理后端就是 `localhost:11434` 的 Ollama —— **与本地共用同一块 GPU**。
2. Hermes 把上下文设为 **131072（128K）**。参照本机历史实测：
   `qwen3.8:27b @ 128K` 常驻约 **28128 MiB ≈ 27.5 GB / 32 GB 显存**。

### 2.4 Hermes 没有外部模型通道

```
auth.json : active_provider = None, providers = {}   （无任何外部供应商凭据）
.env      : 只有 HERMES_LANGFUSE_* 与 HERMES_CUSTOM_LOCALHOST_11434_API_KEY
```

即 Hermes **无法**把推理转出本机 —— 它自己就是本地推理的调用方。

### 2.5 云端模型通道当前不可用

```
POST /api/chat model=deepseek-v4-flash  → ❌ model 'deepseek-v4-flash' not found
POST /api/chat model=glm-5.1:cloud      → ❌ Unauthorized
```

Ollama 云端有 22 个可用云模型（`glm-5.3`、`kimi-k3`、`deepseek-v4-pro`、`qwen3.5:397b`、`gpt-oss:20b` …），
但当前**未登录 / 凭据失效**，走不通。

### 2.6 本机当前显存实况：占用为 0

```
GET /api/ps  →  "models": []        本地无模型常驻
TrackCompass →  LLM_PROVIDER=rule   纯算法，不发任何推理请求
```

**即：TrackCompass 当前对显存零占用 —— 没有可"减少"的量。**

### 2.7 系统内模型调用点枚举（"看下当前系统的任务"）

| 类型 | 漏斗位置 | 调用方 | 绕过点 |
| --- | --- | --- | --- |
| LLM 推理 | `app/agents/base.py:114` → `llm.complete()` | 7 个 Agent 全部经此 | **无** |
| 向量化 | `app/services/embeddings.py:136` → `embed()` | 画像向量化 / 信号入库 / RAG 索引与检索（共 10 处业务调用） | **无** |
| 直连 HTTP | `llm.py:167,175` 与 `embeddings.py:89,108` | 仅这两个适配器内部 | **无** |

**结论**：工程上"所有模型调用改走 X"只需改 **2 个适配器文件**（或仅改 `.env`）。
架构是干净的 —— 问题不在改造难度，而在**选错了落点**。

## 三、为什么走 Hermes 达不到目的

| 维度 | 走 Hermes | 期望效果 | 实际 |
| --- | --- | --- | --- |
| 推理落点 | 本机 WSL Ollama | 转出本机 | **仍是本机同一 GPU**，未变 |
| 上下文 | Hermes 强制 128K | 无影响 | **KV cache 放大**（27B 模型 128K ≈ 27.5GB 常驻） |
| 协议开销 | 登录→ticket→WebSocket→会话→prompt→`message.complete` | 无影响 | 一次调用 6 步往返；一次分析要跑 7 个 Agent，评分页还要高频权重预览 → **延迟不可接受** |
| 可回归性 | Skill 执行型、含文件副作用 | 无影响 | **246 个单测的确定性断言基础失效** |
| 隔离 | 共用 `backend` 账号，无业务用户隔离 | 无影响 | 与多租户 + RBAC + 审计冲突 |

**收益：0。代价：显存上升 + 延迟上升 + 可回归性破坏 + 合规风险。**

## 四、要达到「省本地显存」的目的，正确的 3 条路

### 方案 A ★推荐 — 让推理真正离开本机

| 子方案 | 操作 | 效果 | 当前可行性 |
| --- | --- | --- | --- |
| A1 Ollama 云端 | `ollama signin` 登录后，TrackCompass 指向 `glm-5.3` / `kimi-k3` / `deepseek-v4-pro` | **本地零显存** | ⚠️ 当前 Unauthorized，需先登录 |
| A2 外部 OpenAI 兼容 API | `.env` 设 `LLM_PROVIDER=openai` + `LLM_BASE_URL` + `LLM_API_KEY` | 本地零显存 | ❌ 公网不可达（OpenAI 官方 000） |
| A3 另一台机器 | 指向你那台机器的 `:11434` 或 vLLM `:8000/v1` | 本地零显存 | ❓ **需你告知是否存在第二台机器**（本次探测确认 192.168.2.192 是本机） |

切换成本：**改 `backend/.env` 2–4 行 + 重启**，业务代码零改动。

### 方案 B — 降低 Hermes 自身的上下文（治本，因为它是显存大户）

> **本节数字已由 Ollama 日志实测修正**（2026-09-14）。此前粗估「释放 15GB+」是**估算错误**，
> 把 KV 总占用误当成了可释放量。实测真值见下表。

**qwen3.8:27b 在两种上下文下的实际显存明细**（来源：`journalctl -u ollama` 中
`llama_context: n_ctx` 与 `llama_kv_cache: CUDA0 KV buffer size` 配对记录）：

| 配置 | 权重 (CUDA0 model buffer) | KV cache | 合计 |
| --- | --- | --- | --- |
| **@128K（当前）** | 15,339.44 MiB | **8,192.00 MiB** | **23,531 MiB ≈ 23.0 GiB** |
| @64K | 15,339.44 MiB | 4,096 MiB | 19,435 MiB ≈ 19.0 GiB |
| **@32K（建议）** | 15,339.44 MiB | **2,048 MiB** | **17,387 MiB ≈ 17.0 GiB** |

KV cache 与 `n_ctx` **严格线性**。参照同为 Qwen 系的实测：`qwen2.5:7b @32K → KV = 1,792 MiB`。

> **128K → 32K 真实可释放：约 6.0 GiB（不是 15GB）。**

**但比降上下文更有效的是这一条** —— Ollama 服务当前配置：

```ini
Environment="OLLAMA_MAX_LOADED_MODELS=3"     # ← 允许 3 个模型同时驻留显存
```

实测到的并发驻留组合：`qwen3.8:27b`(23.0 GiB) + `qwen2.5:7b`(4.1+1.8 GiB) + `bge-m3`(0.58 GiB)
≈ **30.4 GiB / 32 GiB** —— 这才是「显存挤占」的真实机制：**不是单模型太大，而是多模型并发驻留**。

| 措施 | 显存释放 | 代价 | 优先级 |
| --- | --- | --- | --- |
| `OLLAMA_MAX_LOADED_MODELS=1` | 避免并发驻留（实测最高可省 ~6.3 GiB 的第二个模型） | 切换模型时需重载（首次变慢） | **★★★★★** |
| `num_ctx` 128K → 32K | 约 6.0 GiB | 长会话/多轮工具调用更早截断 | ★★★★ |
| `num_ctx` 128K → 64K | 约 4.0 GiB | 折中，余量充足 | ★★★ |

> ⚠️ 两项都属 **Hermes / Ollama 侧配置变更 + 服务重启**。
> 按你的红线（禁止在 Windows 侧操作 Ollama 服务），**我不擅自动**，需你明确授权。

### 方案 C — 保持现状（零显存，且最稳）

TrackCompass 用规则引擎：**零显存、输出确定、246 单测全部有效**。
需要真实语义能力时，临时切小模型（`qwen2.5:7b` = 4.68GB，而非 27b 的 17.74GB）。

## 五、若仍决定经 Hermes 中转（技术要求）

**前提：必须清楚这不会省显存。** 仅当目的变为「统一审计 / 统一额度 / 复用 Hermes 的 Skill」时才值得。

若要做，最小改造：

```
backend/app/core/config.py       新增 HERMES_ENABLED / HERMES_BASE_URL / HERMES_USER /
                                       HERMES_PASSWORD_ENV / HERMES_TASK_CWD / HERMES_TIMEOUT_SECONDS
backend/app/services/llm.py      新增 provider == "hermes" 分支（复用现有 _meta 契约）
backend/app/models/              新增 HermesTask（任务记录）
```

硬约束（沿用《Hermes接入评估》§五）：
1. **默认关闭** `HERMES_ENABLED=false`
2. **不进 Agent 编排热路径**，只做异步任务（否则延迟不可接受）
3. 必须补：业务鉴权 / 任务记录 / 并发限流 / 有界重试+幂等键 / 输出校验 / 清理策略
4. **禁止**把 Hermes 会话当隔离边界
5. 会话不可达时**回退**现有 `rule()` 通道
